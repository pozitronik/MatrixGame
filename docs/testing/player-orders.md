# Player command characterization

The `game.player.*` cases link the production engine and reuse the controlled battle fixture described in [Testing](../TESTING.md#controlled-battle-scenarios). They add no production access seam and change no gameplay. These are executable increments toward the [behavior catalog](../research/75-behavior-baseline/README.md), not acceptance of the complete baseline.

## Running the suite

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.(player\.|cheats\.intentional_crash$)'
.\tools\test.ps1 -Configuration Release -Filter '^game\.(player\.|cheats\.intentional_crash$)'
```

Use the same filter with `-Cheats` to exercise the form's enabled-cheat dispatch, and without it to check that gameplay input cannot activate cheats. `game.cheats.intentional_crash` runs the production cheat parser in a separate bounded process: its SIGABRT handler converts the intentional abort to exit code 86. The child disables MSVC CRT abort dialogs so an unattended run reaches that signal handler. Returning normally, another failure code or a missing probe-entry marker fails the wrapper. This checks the parser's intentional termination contract even when the form's cheat entry is disabled; it is not a battle golden and does not allow accidental engine crashes.

All checks use `MG_CHECK`, including Release. Each CTest process has its ordinary 30-second limit, except the four command lifecycle cases, which have a 90-second limit for their complete profile matrices; the abort wrapper has a 15-second outer limit and a 10-second child limit. Battle advancement retains the shared fixture's frame and wall-clock bounds. Debug checks for leaked tracked allocations after each case.

## Execution profile

Movement and command scenarios use seed 79, 10 ms map steps, synthetic wheel chassis, the shared fixed obstacle and real generated geometry, synthetic audio, and the fixture's recorded x87 policy. Explicit move, context move and UI-button move each run for 1,500 steps in each supported RNG mode. The test compares all ordered production snapshots at every boundary, including raw floating-point bits and RNG draw count, within that same build and mode. This comparison establishes equality of those three entry routes in this fixture. It does not establish cross-compiler equivalence or compare the build with an accepted historical reference.

The tested command routes reach `CFormMatrixGame::Keyboard`, `CIFaceList::PlayerAction` and the production side mouse handlers. Targeted command hit results are supplied at the side-handler boundary. Selection cases instead project the generated meshes and run their production `InRect`/ray picking through form mouse dispatch, with a supplied visible-object order; they do not test frustum culling, draw-list sorting or native window messages. The UI button has a real `CIFaceElement` carrying the production action name, without rendered artwork. The command fixture initially selects its robots. The group-add and 30-selection-limit cases create additional chassis through the existing geometry factory, but do not advance those enlarged worlds. A separate overlapping enemy used by `mesh_selection` has an ordinary AI team assignment and participates in the subsequent map ticks.

Direct preconditions are separate from command-route evidence: `control_groups` and `independent_group_commands` supply one-member subsets through `CreateGroupFromCurrent(robot)` and `Select(ROBOT, nullptr)`; `mixed_auto_selection` combines existing auto-mode groups through `GetCurSelGroup()->AddObject`, `AddToCurrentGroup` and `Select(GROUP)`. `manual_control` calls `OnForward`/`OnBackward` directly to characterize movement transitions, rather than claiming form-key dispatch for those calls. `group_add_cap` is a component check; its form-route counterpart is `shift_rectangle_group_cap`. After combat death, `manual_combat_death` directly selects the survivor through `CreateGroupFromCurrent(survivor)` and `Select(ROBOT, nullptr)` before checking form-driven manual entry/exit; it does not exercise selection input for that setup.

The suite asserts selection identities and UI flags directly. Its move-route comparison keeps the shared robot/group snapshots in memory and reports the first differing boundary; these cases do not emit persistent JSONL traces or transient internal events. The shared harness's original `game.scenario.*` trace files remain a separate evidence source. Final baseline capture still needs persisted reference/candidate recordings with the complete agreed manifest and integration revision.

`empty_control_group` recalls an unassigned number with and without a current selection. It preserves the selected identities or empty selection and cancels an active move preorder. `control_group_camera` assigns a real number group and calls the form twice: intervals of 0 and 190 ms center the camera on the first member with the existing 100-unit vertical offset; equality at 200 ms and a 210 ms interval perform ordinary recall without changing the camera. Each RNG mode runs separately. A different number key primes the function's static recall history before every case, and elapsed time comes from production map ticks.

`debug_reinforcement_reset` presses F with a landscape or absent trace at zero and positive reinforcement cooldowns. Debug resets the cooldown; Release leaves it unchanged. This route is controlled by `_DEBUG`/`_RELDEBUG`, independently of the cheats option. The separate `debug_building_reinforcement` case adds friendly/enemy/neutral building targets, enabled/disabled requests and live carrier/cargo ownership; see the [finite cheat registry and creation guide](80-cheat-registry.md) for its limits and the spawning/queue cases.

The minimap cases configure its production coordinate conversion without textures and submit both explicit and context commands at the side-handler boundary. The target-validation cases register real mesh-free buildings and cannons only while synchronous order processing runs; they do not tick those targets or claim completed capture/combat. The unarmed manual-fire case asserts real fire-order submission, release, reset and mouse turning. Its interface-focus rejection uses a single direct robot logic tick with supplied focus, because a complete map tick recomputes hover from UI artwork. `manual_armed_fire` adds a real assembled laser weapon and production map ticks: holding the form's mouse button damages a stationary enemy, release stops both the fire order and further damage, another press resumes damage, and input reset stops it again. It uses seed 80, 10 ms steps and both RNG modes; aim is supplied at the world-trace boundary. The armed-fire, repair-command and bomb-command cases explicitly run with an unavailable audio backend (`audio = false`); their RNG profile must not be compared to the synthetic-audio movement cases. The form/interface route is covered by `game.presentation.manual_fire_interface_focus`; run it with the presentation suite, since the player filter does not select it. Native alignment and screen picking remain separate.

`mixed_building_selection` intersects a friendly building and robot with the same rectangle and verifies robot precedence in both supplied visible-object orders. `inactive_selection` isolates the selection eligibility predicate: a dying robot and a crazy robot are excluded, while spawn, base-exit and carried states remain eligible. Those state values are supplied only during selection and restored before teardown; the case does not simulate their full lifecycles.

`mixed_selection_lifecycle` extends that scene with a friendly turret and the selected robot's actual death. Sixteen profiles combine both RNG modes, 10/16 ms map steps, forward/reversed visible-object order, and a one-pixel click or a 60-pixel rectangle. All three objects have generated geometry and intersect the actual selection area; production mesh intersection and form mouse dispatch choose the robot over the building, while the form's selection mask excludes the turret. A turret-only rectangle is a positive geometry/negative selection control. The test supplies a lethal gun hit, requires immediate kill credit and removal of the robot from the current group, and selects the building while the dying robot's retained core still points to its debris. Six seconds of complete map ticks retire that core; after clearing the previous building selection, selecting the same area must choose the building again and leave the kill count at one. The unregistered building borrows a surviving robot's mesh and is destroyed before the session. Visibility is supplied afresh for each interaction, never carried across object retirement. This covers the C1 mixed-object lifecycle selection; native screen picking, frustum visibility, draw ordering and rendered highlights remain separate checks. The case retains complete ordered observations and an exact fresh-session replay for each profile; see [recording contents, validation and reference limits](80-selection-recordings.md).

### Direct-control lifecycle

Three additional CMD-05 contracts cover direct-control exit and destruction through `CFormMatrixGame`. `manual_bomb_key` presses the configured detonation key, once with an unarmed chassis and once with an assembled bomb. An unarmed robot remains controlled and alive; a bomber becomes marked for death without entering a strategic bomb preorder. Over six seconds of production map ticks, the bomber leaves manual control and its retained core loses the object. The nearby friendly robot takes one 0.4-point hit in the visible-health scale, remains alive and receives no fire order. The negative case receives no damage. Both use seed 80, 10 ms steps and unavailable audio in each RNG mode; no screenshot or explosion-rendering claim is made.

`manual_combat_death` holds forward and fire through form dispatch, then supplies nonfatal and lethal gun hits at the production `Damage` boundary. Nonfatal damage preserves control. Lethal damage produces the dying state, releases control immediately, restores the movement speed and credits one kill to the attacking side while the object still exists as debris. The fire-button press is checked immediately to ensure that manual control does not start a selection rectangle. The later release comparison checks selection stability; the fixture has no visible-object list, so that comparison alone cannot detect rectangle creation. The physical key state remains held until release; late key/button release preserves the current group and selection kind and cannot transfer motion/fire to the surviving robot. Six seconds of ordinary map ticks retire the dead object's retained core without a second kill credit. The survivor can subsequently enter and leave manual control. The scenario supplies incoming hits directly; it does not establish enemy aiming or projectile collision. Its seed, time and audio profile match the bomb case.

`manual_exit_keys` enters through Space and separately exits through Enter, Space or Escape in both RNG modes. ## Observed legacy behavior

The stop key calls `SelectedGroupBreakOrders` after issuing a group stop; the corresponding UI button does not. Their resulting unit order pools therefore differ immediately, although both stop the prior journey. Tests assert the difference rather than requiring artificial route equality.

Explicit attack accepts a friendly live robot as its target. These unarmed chassis prove command acceptance and replacement only; they do not establish friendly-fire damage semantics.

Patrol's synchronous `TaktPL` switches the return flag before the first externally advanced frame. The suite observes that initial state and requires a later reversal. Auto-capture without any building changes its group intent to stop during execution; retaining `mpo_AutoCapture` indefinitely would be a behavioral change.

Input reset clears held controls and the next robot logic tick removes the manual movement order. It leaves the robot under direct control. Leaving direct control restores its speed and assigns a ground-attack intent before later player commands replace it.

The speed-boost assertion pins the accepted multiplier to `1.1f` rather than reading the production constant as its own oracle. Direct controlled-unit deletion exercises ownership retirement; it does not substitute for damage, dying-state animation or explosion tests.

A rectangle with no eligible hit retains the selected group. For a rectangle whose area is below 9, the first eligible intersecting robot in the supplied visible-object order wins; at area 9, the scan may select both overlapping robots. These checks pin selection behavior while leaving the visibility-order calculation outside the fixture.

In a mixed selection with auto-attack and auto-defence members, the attack flag is already active. The first attack-key press stops the combined selection and clears all three auto flags; the next starts auto-attack for both. Deleting an autonomous target causes another eligible target to be chosen; after all targets disappear, attack/defence intent remains active with a null target.

The first MEGABUST invocation doubles the robots' reported maximum health. Its literal factor 20 is applied to a getter measured in tenths of the initializer's units, so a twentyfold visible-health expectation would change the existing behavior. Repeating the cheat marks ordinary friendly robots for destruction while exempting robots in automatic spawn/base transitions; the test observes that mark without simulating death effects.
