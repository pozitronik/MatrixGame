# Presentation integration evidence

Presentation coverage has two parts: executable state/event contracts and observations from the native game. The former can verify command routing and resource ownership; only the latter can establish what a player sees and hears. Neither part establishes the other. This document maps PRES-01 through PRES-04 in the [behavior catalog](../research/75-behavior-baseline/README.md). Complete-baseline acceptance requires evidence at the agreed integration revision.

## Automated checks

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.(presentation|input|selection|display|device|font|audio|settings|resources|paths|startup)\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.(presentation|input|selection|display|device|font|audio|settings|resources|paths|startup)\.'
```

The new `game.presentation.*` cases link real `CIFaceButton`, `CSound` and standalone sound services. The existing `CommandWorld` supplies map/configuration lifetime, and the existing fake audio device receives decoded synthetic WAVs. These button/audio cases use no game package, window, driver or audible playback. Most button cases begin in explicitly declared focus states. The separate `textured_button_hit_testing` case uses real interface geometry and texture-alpha picking with synthetic pixels; it does not draw the button or use native window messages.

The textured-button case uses a 4 by 4 ARGB texture uploaded through `CTextureManaged` to the shared CPU texture fixture. It contains no artwork from the game. `CInterface::OnMouseMove`, `OnMouseLBDown` and `OnMouseLBUp` perform picking and dispatch; no focus or pressed state is supplied for the successful click. The only directly supplied interaction state is the disabled flag for that rejection check. Tooltip construction and rendered overlap/layer ordering remain outside this case.

The click-name behavior corresponds to inventory item D5. It is an observable legacy choice, not a claim that the name matching was intended. Tests preserve it without changing the condition. Seed 87 is explicit for draw-count comparisons; configuration and WAV data are synthetic and supplied by the case. The six battle-audio cases use the existing battle session with a synthetic mesh/map and non-rendering device, seed 87 and 10 ms ticks. They record backend events rather than audible output or private package contents. Context commands rebuild the selected logic group, so a repeated context move uses the chassis acknowledgement again; direct replacement on an existing group uses the in-progress variant. Missing-backend and missing-mapping profiles have different draw counts and must remain separate reference profiles. Other cases assert discrete routing/lifetime behavior without a battle schedule. Checks are active in Release, and tracked-allocation checks run where instrumentation is enabled.

## Camera input through the game form

Three `game.presentation.camera_*` cases send mouse and keyboard input through `CFormMatrixGame` with the synthetic battle fixture. They update the production camera with `Takt(0)` and `BeforeDraw`, without advancing battle time or submitting rendered frames. The strategy-camera defaults, 1280 by 720 viewport, seed 87 and both RNG modes define the profile. The fixture's cursor surrogate records position without loading cursor artwork or claiming OS capture behavior.

`camera_wheel_limits` measures camera-to-link-point distance from the resulting inverse view matrix. One positive wheel step moves from 250 to 209.5 world units; the opposite step restores 250. Repeated steps saturate at 115 and 790, further steps cannot cross either limit, and zero wheel input at the unclamped distance of 250 changes nothing. The reset key preserves wheel distance. Distance checks allow 0.001 world units for matrix reconstruction roundoff.

`camera_drag_release` verifies middle-button ownership, cursor-delta rotation (a 20-pixel move adds 0.2 radians of yaw and sets pitch to 46 degrees), both configured pitch endpoints, release without further rotation, and keyboard restoration of the original orientation. The configured pitch parameter runs from 60 degrees at its zero endpoint to 20 degrees at its one endpoint, so downward pointer movement increases the resulting angle. Wheel and drag/reset routing must consume no RNG draws.

`camera_input_interruption` repeats a drag across deactivation, explicit input reset and pointer leave. Each event cancels mouse-camera mode; deactivation/reset also clear the held button, while pointer leave retains its key state until release. A subsequent move and late release must not rotate the camera. A fresh middle-button press must restore normal rotation. These are form-handler and camera-state contracts; native focus delivery, pointer confinement, image continuity, camera scrolling and rendered picking remain required evidence.

## Interface focus and manual firing

`game.presentation.manual_fire_interface_focus` delivers pointer movement and button transitions through `CFormMatrixGame`, then advances complete production map ticks. A generated 4x4 texture provides opaque and transparent texels for a visible, always-on-top interface button. The normal interface pass performs geometry and alpha hit testing and selects the focused interface/element; the fixture never assigns `m_InFocus` or the focused element directly. The always-on-top setting keeps this independent synthetic panel visible through `CInterface::Init`, as required for repeated-frame input delivery.

A press over an opaque texel puts the button into its pressed state and remains held without creating a fire order or damaging the target. Moving onto a transparent texel in the same element bounds releases interface focus and allows firing at the supplied world target. Moving back over an opaque texel while holding fire retains the existing fire order and continues damage. This is the observed distinction: interface focus blocks starting fire, but does not cancel firing already in progress. Releasing the button over the interface stops firing; leaving the interface without pressing again does not restart it. Direct-control identity persists until the explicit Enter exit.

The case uses a real laser-equipped robot and damage receiver, both RNG modes with seed 87, separate 10/16 ms schedules and unavailable audio. Assertions cover focus/element identity, held input, fire-order transitions, actual health changes and stable health after release. World picking remains a supplied trace; the test does not render pixels, deliver OS focus events or prove native pointer alignment. This is shared PRES-01/CMD-05 hover/fire integration evidence. Settings-window input consumption and the remaining presentation baseline retain their separate requirements.

## Native standalone startup failures

Five `game.startup.native_*` cases execute the built standalone game in fresh synthetic deployments. Each deployment copies only the EXE into a directory whose name contains spaces, Cyrillic and Japanese characters, then starts it from a different working directory. A private, non-input Win32 desktop contains its native diagnostic dialog; the test never switches the visible desktop. It reads and dismisses that owned process's dialog, verifies exit code 1 and inspects the startup log. Child processes start suspended, join a non-inherited kill-on-close job, then resume. Bounded waits and explicit termination handle ordinary failures; the job also terminates the child if the harness is killed without unwinding. Process/desktop/job handles and synthetic deployment directories are released after ordinary completion. An interrupted harness can leave its synthetic directory, but no running child. These cases are registered for EXE builds only.

| Case suffix | Asserted startup contract |
| --- | --- |
| `native_missing_resources` | A required package placed only in the caller's directory cannot satisfy the executable-directory resource check. The game displays `Game resources required`, gives the `DATA/robots.pkg` placement instruction and exits before initializing the RNG. |
| `native_rejected_packed` | With a synthetic empty-root required package beside the EXE, a rejected packed configuration produces the `Invalid packed configuration` diagnostic and exits through the initialization-failure path. |
| `native_missing_text` | Without a packed configuration or loose text configuration, initialization reports `cfg\robots\data.txt` as the missing file and exits. |
| `native_invalid_random` | An invalid `RandomGenerator` value reports fallback to ParkMiller before the deliberately rejected packed configuration ends startup. This establishes the early startup choice; it does not claim that a battle loaded with that choice. |
| `native_damaged_optional` | All four combinations of absent or malformed `sound.pkg` and `voices.pkg` reach the same later packed-configuration failure. Each present malformed optional package is reported unavailable; absent optional packages and the valid empty-root required package produce no package-open failure. |

The 16-byte required package is independently encoded synthetic data; it contains no playable resources. The packed-configuration rejection fixture is an eight-byte header, and malformed optional packages contain one byte. No original package, graphics device or audio device participates. The child resolves the helper's verified D3DX runtime and the configured compiler's runtime directory through its temporary PATH, so a `TestsOnly` build deliberately builds the standalone EXE as a test dependency without staging game assets. The tests retain the normal startup, package opening, configuration loading and failure-cleanup implementations, and reject a logged standalone cleanup failure.

The observer reads the foreign dialog's cached caption with `GetWindowTextLengthW` and `GetWindowTextW`; it sends bounded text messages only to the child controls. A complete observation requires a nonempty caption, body text and one enabled button. A failed or early empty caption observation is retried within the existing deadline rather than accepted and dismissed. The individual scenarios still assert the exact expected titles. Captured captions are printed, and an incomplete observation reports its caption-read error, body length and button count. This follows the Win32 distinction between [foreign window captions and control text](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtextw).

The additional `game.startup.native_diagnostic_readiness` case starts the test executable itself on a private desktop. Its hidden synthetic dialog publishes its body and sole enabled button before its caption. Named events hold that state until the parent has verified rejection; the child then supplies the caption and the parent requires a complete observation and clean exit. The dialog procedure refuses `WM_GETTEXTLENGTH` and `WM_GETTEXT`, while its Static child handles text messages normally, so successful capture establishes the foreign cached-caption path. This case uses no game resources, graphics device or original game process and does not prove why an earlier CI caption observation failed.

These checks cover native failure dialogs and early initialization in both build configurations. They do not establish successful fresh-release installation, usable packed/text battles, rendered or audible output, full-package corruption recovery, map-argument CalcVis launch/log/exit, menu quit, Alt+F4 or loaded-map teardown. Those P3 requirements remain in the native procedures and validation ledger. The synthetic malformed packages exercise package-open rejection only; they cannot establish behavior for every corrupt archive entry.

## Settings input, pause and persistence

`game.presentation.settings_input_pause_cancel` opens the production battle menu with Escape, then opens `SettingsWindow` through C or a click on the menu entry. Both entry paths run independently under ParkMiller and LegacyCRT with seed 87 and 10 ms map ticks. A moving robot assigned to control group 1 supplies an observable battle state. Opening the normal menu clears selection; pressing 1 while settings are open must not recall the assigned group. A separate, explicitly supplied stress precondition then reselects one robot while the modal window remains open, making the remaining command checks actionable. M cannot enter order mode, Ctrl+2 cannot reassign that robot's control group, and the typed `NEED4SPEED` sequence cannot change the speed flag. Pause cannot resume the battle from inside the dialog. Repeated production map ticks preserve simulation time, robot position and its existing order. After Cancel and a second Escape to leave the battle menu, simulation time and movement resume. The real group-1 recall restores both assigned robots, then the same Move and group-assignment inputs take effect. The cheat sequence toggles speed only in cheats-enabled builds, with an unchanged flag required in cheats-disabled builds. The enabled profile is essential to establish cheat interception.

A mouse change to camera speed produces a pending 125% label without changing the effective 100% speed. Cancel returns to the paused battle menu, discards the change and creates no settings file. `game.presentation.settings_apply_save_failure` additionally navigates the selected row with Left/Right, changes volume and a restart-only skybox choice, then attempts Apply against an existing read-only settings file. Save rejection must retain the open, paused dialog, produce the error text, preserve the previous file byte for byte, remove the temporary file and leave runtime settings unchanged. Removing the read-only attribute and applying again saves the pending values, updates camera speed to 125%, retains the running skybox and records the new skybox as restart-pending. Loading the saved file must reproduce the applied settings. Apply returns to the paused menu; the following Escape resumes the battle.

The executable links the production form, settings window/model, hint composition, map/menu lifecycle, runtime settings and file persistence. A test-only `IDirect3D9` adapter enumerates exactly 640x480 and 1280x720 and resolves the monitor of the fixture-owned window; other adapter operations abort. The existing CPU device stores the composed hint textures and rejects drawing. A link-time `Text::Render` surrogate supplies text-sized opaque rectangles and records the requested text; it does not draw glyphs or call D3DX. The menu template, button-hole bitmap and empty hint-button panel are synthetic. Apply and Cancel use the real Enter/Escape handlers; this fixture does not test artwork-dependent OK/Cancel button picking. Initial selection and the context-command world trace are supplied by the battle fixture; the additional modal re-selection is a declared stress precondition, rather than normal menu behavior. These two cases use no native window, packages or audio device.

Sensitivity checks in Debug and Release with cheats enabled reject three independent changes: allowing M past modal keyboard interception, feeding the cheat parser before settings consumes input, and applying settings after a failed save. These temporary mutations are not part of the source tree.

These contracts establish automated input isolation and the listed pause/save/apply/cancel consequences. They do not establish native focus delivery, glyph rendering, localized/small-window layout, audible volume changes or the full settings baseline. The separate display case below adds settings-driven reset and rollback state contracts. Those requirements remain in P4 and its native procedure.

## Settings-driven display rollback

`game.presentation.settings_display_rollback` opens the real menu and settings dialog while a control-group-assigned robot follows a Move order. Mouse input changes the resolution from 1280x720 to 640x480, the mode from Windowed to Exclusive and camera speed from 100% to 125%; Enter invokes the production save and runtime-apply path. The test consumes that queued request through `Display::apply_pending`, without calling the lower-level reset helper directly. Both RNG modes use seed 87 and separate 10/16 ms schedules.

An opt-in callback on the CPU test device rejects the requested reset with `D3DERR_INVALIDCALL`, then accepts the rollback with `D3D_OK`. Assertions cover release/reset/rollback/restore ordering, the requested and restored presentation parameters, retained presentation interval, protection against device mutation of the parameter copy, screen dimensions, mode/fullscreen flags and consumption of the queued request exactly once. The actual form receives input reset; a held arrow key and the map's remembered key clear. The battle stays paused with unchanged simulation time, robot position and existing order.

The saved request remains 640x480 Exclusive after this rejected device reset; the effective display returns to 1280x720 Windowed. Camera speed remains 125%. This is the current contract, including its persistence distinction: the file is not rewritten to the effective display. Reopening settings shows the effective mode and size, while Cancel preserves the saved bytes. Leaving the menu resumes the original movement, control-group recall allows a fresh Move order, and new key presses/releases work. A subsequent settings Apply successfully selects 640x480 Windowed, updates effective and saved state, and leaves no extra pending reset.

This case owns a hidden top-level Win32 window on the caller's current desktop so the production window-style/size code and monitor lookup execute; it does not create a private desktop. The CTest label `current-desktop` allows callers to exclude it as described in [Testing](../TESTING.md). Only this test executable's `ClipCursor` and `GetCursorPos` imports are intercepted: the inactive-window profile records release calls without changing the desktop cursor and supplies no native pointer position. The CPU device still rejects rendering, and its Reset callback provides declared HRESULTs rather than a native GPU reset. Resource callbacks record ordering; they do not establish GPU-resource recreation, rendered continuity or native focus behavior. No game packages or audio device are used, and no interactive window appears.

A sensitivity check in Debug and Release removes only the queued resolution request from `StandaloneSettings::apply_runtime`. The case then fails on the first reset's expected 640x480 parameters. Restoring that statement restores all three settings-case passes. The temporary mutation is not part of the source tree. Native display, glyphs, pointer alignment and audibility remain separate acceptance observations.

## Positional audio boundaries

`positional_attenuation_boundaries` uses the existing looping laser mapping with attenuation 0.5 (the frontend scales it to 0.001), volume endpoints 0/1 and pan endpoints -1/1. It checks raw frontend `CalcPanVol` outputs before the standalone service clamp, then actual standalone voice parameters at the camera center and on both sides at distances 199, 200, 201, 700, 1,199, 1,199.9, 1,200, 1,201 and 2,000. Frontend volume must be exactly 1 at distances 0 and 199, and exactly 0 beyond 1,200; the other samples and pan allow 0.00001 for floating-point rounding. At nominal distance 1,200, camera-relative coordinate rounding can leave a tiny positive raw volume (observed 2^-24), which must still be rejected by playback. Volume stays at one through 200, then matches 0.999, 0.5, 0.001 and 0.0001 at the intermediate samples. The 1,199.9 sample must still create a voice, tightening the rejection-threshold check. At and beyond 1,200 a new sound is rejected without allocating a voice. Center pan is zero and lateral samples pan fully to the corresponding side. Each created voice is stopped and destroyed once; the PCM clip loads once and positional calls consume no RNG draws.

`positional_loop_reentry` distinguishes creation from updates. An initially distant sound creates no voice and loads no PCM; bringing its empty handle to the center creates a loop. Moving that active loop out of range makes it silent but retains its handle and voice. Returning it on the opposite side restores attenuated volume and pan without allocation. After an explicit stop, ChangePos rejects the stale handle; Play with that handle creates a different voice using the cached clip. Clear destroys each remaining voice exactly once. Both cases run under both RNG modes with seed 87, without advancing simulation or opening an audio device. They extend PRES-02 routing/lifetime evidence; actual audibility, native spatial perception and full resource-backed scenes still need separate validation.

## Weapon-owned loops

The two `weapon_positional_loop_*` cases create a real laser effect through `CMatrixEffect::CreateWeapon` and start firing through `FireBegin`. The synthetic configuration declares a one-unit upward ray, a 1,000 ms cooldown and looping laser audio with attenuation 10 (scaled to 0.02). Four 10 ms weapon ticks produce exactly one shot; no map tick or gameplay command is advanced. Both RNG modes use seed 87. The existing fake audio backend retains a playing loop until its production owner stops it; the emitted profile identifies this audio policy separately from the base battle fixture's unavailable backend.

The first shot creates one fully audible voice 25 units to the camera's right. Moving the strategy camera 50 units along that axis and recomputing its matrices makes the weapon's next tick pan the same voice left. Moving the effect 260 units to the right of the new listener makes that voice silent without destroying it. Moving it 225 units left restores half volume and left pan. These assertions use the production weapon's automatic `ChangePos` call, without direct sound-position updates from the test. No second voice, extra PCM load or additional RNG draw is allowed during those updates.

The stop case calls `FireEnd` twice and requires one immediate voice destruction; deleting the effect and clearing sound cannot destroy it again. The retirement case instead deletes the still-firing effect and requires its destructor to stop the voice before global audio cleanup. This covers component ownership and camera-relative updates through the weapon implementation. Robot movement and deletion through full map ticks, audible playback, native camera input and all other weapon types remain separate scenarios.

The separate [audio continuation cases](87-audio-continuations.md) now cover reuse of a weapon's loop across repeated shots and camera-driven updates of `AddSound` positional sounds through ordinary map ticks and `CSound::Takt`. The earlier weapon cases remain one-shot owner-position/stop controls; robot-lifecycle and native listening evidence remain separate.

## Clear-rectangle regression

D1's vertical-start error is corrected in `CIFaceElement::BeforeRender`: a depth-clear rectangle uses its configured `top` offset for `y1`. At element image position `(100,200)`, `ClearRect=(3,11,20,30)` now submits `(103,211,120,230)` instead of `(103,203,120,230)`. The configuration parser already reads separate left/top/right/bottom values; the correction changes one coordinate expression, without changing configuration formats, class layouts, simulation or command dispatch. It applies to EXE and host DLL rendering, including external interface configurations with unequal left/top offsets.

Three registered `game.presentation.*` cases call the production method and inspect its actual clear-rectangle buffer. `clear_rectangle` retains the original asymmetric correct-result reproducer. `clear_rectangle_states` checks six explicit position/offset combinations in all five image states: left smaller/larger than top, negative local offsets, a negative element origin with a positive resulting rectangle, zero offsets and equal offsets. Other image-state positions and the element origin deliberately differ, so the active image geometry must be used. `clear_rectangle_disabled` checks all five states without the flag: the texture is still preloaded, but no clear rectangle is appended. Every sample verifies texture-reference release and clearing the submission buffer.

Before the source correction, the asymmetric and state cases fail on the vertical coordinate while the disabled control passes. Afterwards all three pass. `PreloadedTexture` acknowledges residency notification only and aborts on other resource operations; no drawing or texture upload is simulated. These assertions establish the submitted rectangle, not visible corruption in supplied assets. The renderer consumes this buffer in its Z/stencil clear paths; actual native appearance remains separate presentation evidence. The legacy command `probe.presentation.clear_rectangle` is retained as an alias and now succeeds.

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.presentation\.clear_rectangle'
.\tools\test.ps1 -Configuration Release -Filter '^game\.presentation\.clear_rectangle'
```

Repeat with `-DLL` for the host-library build. D1 belongs to #87 correction/disposition, with original reproduction in #89 and scaling overlap in #63. This bounded correction does not implement interface scaling or complete the presentation baseline.

## Native preparation

Use the pinned build helper, then follow [configuration preparation](../PLAYTESTING.md#prepare-the-configuration-cases). Test Debug/Packed, Debug/Text, Release/Packed and Release/Text separately with cheats disabled. Build before removing the output copy of `CFG/robots.dat` for text mode: rebuilding stages it again. Rename backups with a different filename prefix, since suffix-only backups can still be discovered. Leave all root-level supplied packages unchanged and untracked.

For each build, launch from its own executable directory and capture the exit status. For example, after preparing Debug's configuration and package copies:

```powershell
$playtestDirectory = Join-Path (Get-Location) 'build/mingw-debug-exe/MatrixGame'
$playtestExecutable = Join-Path $playtestDirectory 'MatrixGame.exe'
Get-FileHash -Algorithm SHA256 -LiteralPath $playtestExecutable
$playtestProcess = Start-Process -FilePath $playtestExecutable -WorkingDirectory $playtestDirectory -PassThru -Wait
$playtestProcess.Refresh()
$playtestProcess.ExitCode
```

For Release, replace `mingw-debug-exe` with `mingw-release-exe`. Run only one game at a time. This command intentionally opens the interactive game; it is a manual procedure, not part of CTest.

## Native procedures

Use the [P1-P4 procedure supplement](87-native-procedures.md) for the shared launch/deadline/exit/restoration record, qualified active-loop scenes and exact staged startup-failure substitutions. It reuses the steps below and existing public guides; it records no native execution.

Run the following in each of the four configuration cases. Use the arrow keys for strategic camera scrolling; W is a direct-control key. Record any unavailable scene/target as unperformed rather than passing it.

1. Start windowed at 1280×720 with both audio packages and no loose `CFG/sounds.txt`. In the startup menu choose New battle, select the scenario map and bonus explicitly, and start it. Record `Map`, `BattleBonus` and the effective difficulty multipliers; use None unless the scenario specifies another bonus. Confirm map, robot/building geometry, text, minimap and introductory controls. Dismiss the introduction, select a friendly robot, press M and click nearby open terrain. Verify the selection/move acknowledgement, visible order and arrival. Trigger a reachable attack and observe projectiles, damage and battle audio.
2. Drag a selection rectangle quickly for ten seconds, release, then give a move order. Repeat in the opposite drag direction and with an immediate release. Start another drag, press 1 while holding the mouse button, then release; the canceled rectangle must not add units. Follow the exact [selection procedure](../PLAYTESTING.md#selection-dragging) for expected membership and exit checks.
3. While scrolling with an arrow key, switch away without first releasing it. Return and release all controls; the camera must remain stopped until a fresh input. Repeat during a selection drag and middle-button camera rotation. Cursor release and any mode-dependent minimization must be recorded. Compare camera position before/after return; a minimized window alone cannot demonstrate stopped movement.
4. Press Alt+Enter twice, both during normal play and with the introduction or battle menu open. Verify viewport, cursor/picking alignment, selection, text and continued commands. Repeat the [display procedure](../DISPLAY.md) for borderless/exclusive startup and toggling at supported adapter resolutions. Do not select an exclusive resolution absent from that adapter's modes.
5. ## Evidence record

For every native case record: source revision and binary SHA-256; toolchain and build/options including cheats/assertions; map/configuration identity, effective difficulty and RNG mode; package presence and private hashes; packed/text mode; resolution, display mode, adapter and Windows scaling; steps completed, observations, exit code and relevant diagnostics. Screenshots may support visual claims but cannot replace command/state observations. Keep copyrighted packages, extracted assets and private configuration out of public evidence.

Required native profiles: Debug / Packed, Debug / Text, Release / Packed and Release / Text. Record execution status in the contribution evidence.

Earlier playtests from other changes require an applicability check against the selected revision/profile. Record reused, pending, passed and failed cases separately in the [validation ledger](native-validation.md). Native execution may be deferred independently of completed implementation; before accepting the complete baseline, attach the required reviewed records and explicitly dispose of every missing or failing case above.
