# Behavior baseline completion checklist

This reconciliation covers the command, navigation, AI and presentation work packages at integration revision `8594270ed9a9634557d1fe9dc00528e49789c077`, with later evidence credited in the rows below. The [behavior catalog](../research/75-behavior-baseline/README.md) defines the required behavior; the subsystem guides describe implemented assertions. This document credits shared evidence and turns their remaining scenario descriptions into reviewable work units. Battle outcomes and repeated sessions have a separate [outcome coverage map](85-battle-outcomes.md) and a [proposed finite completion plan](85-outcome-completion.md), reconciled at its own stated revision. That plan assigns the shared outcome/session portions of C7 (O5/O8), A8 (O7/O9), P3 (O6/O7) and P4 (O6/O7), and preparation of native groups NV-05/NV-06 (O10). Those rows remain work to deliver; the plan does not establish their implementation or baseline acceptance.

The scenario selections below are the proposed finite completion boundary for these four packages. Review of this document must confirm that selection against the catalog. A row describes work to implement or evidence to reconcile, not a passing test. It does not accept a reference revision, waive a catalog variant, or authorize structural changes. If an implementation discovers a missing behavior, identify the affected catalog entry and obtain a scoped addition rather than treating every possible input combination as an implicit requirement.

## Implementation closure and deferred execution

Implementation and native execution have separate completion records. An implementation PR may merge after its own reviewed scope and required CI pass. Its issue may close after the required code, automated scenarios, fixtures/tooling and exact native procedures are delivered, with all pending native cases explicitly handed off to [native validation](https://github.com/pozitronik/MatrixGame/issues/191). The completion comment links the merged revisions, actual automated results, procedure versions and outstanding case IDs. Missing automated tests, failed checks and unresolved implementation defects remain implementation work.

The [native validation ledger](native-validation.md) collects unperformed execution and applicability checks for older evidence. Execution is deferred until the maintainer is ready or suitable reviewed pre-baseline tooling can perform the applicable checks. An API observation must still prove the property under test; rendered pixels, OS focus and audible output need suitable observations. The production AI API depends on baseline acceptance and is not a prerequisite for this task.

The [complete baseline](https://github.com/pozitronik/MatrixGame/issues/69) retains reference/comparison records, integrated checks, coverage/performance measurements and explicit acceptance. It is blocked by the native execution task even after implementation issues close. Deferred or failed execution never counts as a pass. Preparing procedures and running automated regressions may continue while native execution is deferred. The checklist's scenario selection remains subject to review; this accepted tracking split does not reduce it.

## Completion rules for implementation rows

Each automated row needs named CTest cases linked to production code, explicit fixture inputs and a bounded command/tick schedule. Record the resulting intent, physical outcome, lifetime and RNG observations relevant to that row. Determine expectations from measured reference behavior; a proposed scenario does not prescribe a more desirable game rule. Run both supported RNG modes where applicable, MinGW Debug/Release, and the supported MSVC/x86 DLL CI configurations. Time-dependent scenarios use the catalog's separate 10/16 ms profiles where applicable; any narrower schedule needs a documented reason. Cheats, `_DEBUG`, `_TRACE` and host-only behavior use only builds that expose the path.

A row's implementation is complete when its automated variants have assertions and review evidence, or when existing cases establish those same variants, and any required native procedure/setup is delivered. Record native execution separately in the linked ledger; a prepared procedure is not an executed case. A shared row has one implementation owner; other packages link its evidence rather than making duplicate fixtures.

The common [schema-1 reader/comparator](../../tools/compare-battle-traces.py) accepts only `header`, `command`, `snapshot` and `complete` records. It rejects duplicate JSON keys, non-finite JSON numbers, backwards snapshot frame/time/draw counts, unknown record types, incomplete tails and anything after completion. Completion must immediately follow and match the final snapshot. It validates the range of integer `_bits` fields; that is not a general finite-floating-point oracle or a fixture-specific required-field schema. Default exact comparison ignores only the header's `revision` and `dirty` provenance. Its explicit diagnostic `--allow-profile-difference` option additionally ignores the enumerated build/compiler/assertion/precision/compatibility fields; scenario, seed, RNG, audio/render policy, unknown fields and all subsequent records remain exact. That diagnostic result is not same-profile baseline evidence. A semantic validator must separately require its scene's observations so two equally incomplete files cannot pass by equality.

The shared [`Session::snapshot`](../../tests/battle_scenario.cpp) serializes the original four registered robots, their lifetime/position/health/group/intent/destination, and occupied player-group counts/targets. Its order array is `[type, phase, param1_bits, param2_bits, object]`: it omits `m_Param3` and `m_Param4`, does not describe newly created actors automatically, and is not a complete engine-state dump. These omissions include initialized, meaningful state: production `Fire` orders use parameter 3 for aim height and parameter 4 for firing/repair mode, read by the [robot logic](../../MatrixGame/src/MatrixRobot.cpp). N5's extended actor observations retain all seven order fields; the [manual-exit observer](../../tests/player_order_scenarios.cpp) separately retains parameter 4 but still omits parameter 3. An adapter must preserve each selected case's existing custom observations and explicitly retain any additionally asserted aim/queue field, resources, created-entity identity or lifetime boundary needed by its contract. Relabeling the shared five-field array as a full queue would hide that gap; changing the production order model is unnecessary.

Persisting a field and checking its type are separate responsibilities. At the inspected integration revision, selection required a live actor's `queue` key without validating its array/entry shape; N5 checked three parameter-bit ranges but not the integer type of every remaining order field, including `param4`. This preparation tightens the selection, automatic-order and navigation consumers around their existing five-field Session and seven-field extended queue layouts. It rejects malformed containers, scalar types, bit widths and normalized identities independently of replay equality; automatic-order checks also require boolean liveness and the producer's omission of queues for dead actors. Producers, record kinds and recorded values are unchanged. These guards do not add the missing parameter 3/4 observations to the shared Session queue or establish all custom-field, compiled-identity and scenario guarantees still required by G2.

#### Episode, completion and comparison boundaries

Keep one schema-1 header and one successful completion per declared episode, with the actual configuration, RNG/seed and source identity. A fresh Session or reseed is an episode boundary; a map reload may intentionally retain its clock and RNG. Preserve those measured differences. The current parser rejects a second header in the same file, and its snapshot clocks/draw counts cannot go backwards. Multiple files linked by explicit caller/case/episode/context metadata can retain those boundaries without adding an unrecognized `episode` or `reseed` record type, resetting observed counts for convenience or weakening the reader.

A new adapter must truncate its owned output before setup can fail, retain the last safely completed boundary where its existing observation model permits, and withhold completion after a failed required journey, replay, prefix or final assertion. Post-run wrappers may have no snapshots when a run fails; identify that limitation rather than manufacturing a complete tail. Existing auto/shared-harness/combat tails have the earlier caller boundary documented above; preserve process/CTest success and make any completion-strengthening change a scoped test-tooling review. No file tail by itself proves teardown, native presentation or the required repeated-session case.

Keep corpus inventories finite and context-specific. Preserve the necessary original/custom actor and queue/resource/lifetime fields, and test required-field/type/schedule guards independently of pair equality.
