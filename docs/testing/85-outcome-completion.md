The [behavior catalog](../research/75-behavior-baseline/README.md) remains authoritative. The [outcome guide](85-battle-outcomes.md) describes existing assertions; this document selects the remaining scenarios and assigns shared work. Its selection requires review. It neither records new passing tests nor accepts a historical reference or the complete baseline.

Native execution may then remain with [native validation](https://github.com/pozitronik/MatrixGame/issues/191). Reference comparisons, measurements and acceptance at an exact integration revision remain with [the complete baseline](https://github.com/pozitronik/MatrixGame/issues/69).

## Scenario and observation rules

O1-O10 are local work-unit IDs, not additional tracker issues. Each row states a selected scene or transition, not an exhaustive cross-product of all game inputs. Use both supported RNG modes for simulation cases and separate 10/16 ms schedules for newly added map-tick cases. Existing narrower schedules retain their documented limits; extend those cases where a row explicitly requires it. A wall-clock loop or OS process test needs its own bounded timing profile instead of pretending to execute fixed map ticks.

Each implementation records seed, effective configuration, fixture revision, commands, deadlines and observations before/at/after the transition. Assertions must remain active in Release. Verify Debug and Release and obtain supported compiler/x86 DLL CI evidence; mark EXE-only or host-only cases explicitly. Persisted historical comparisons and final same-revision validation are the G1-G5 obligations in the [baseline checklist](baseline-completion.md#integrated-acceptance-evidence).

Expectations must follow measured production behavior. For example, the result scheduler's 2020/2032 ms dialog boundaries are already characterized; they must not be replaced with a guessed one-second deadline. Wall-clock statistics use the existing bracketing/sign observations unless a clock seam is separately reviewed. An assertion about reset must distinguish state actually reset from state deliberately retained; it must not prescribe a new lifecycle policy.

## Three different session boundaries

The production paths are materially different:

- **Restart current battle:** `OkResetHandler` in [MatrixMap.cpp](../../MatrixGame/src/MatrixMap.cpp) calls `CMatrixMap::Restart` in [MatrixMapPrepare.cpp](../../MatrixGame/src/MatrixMapPrepare.cpp). It clears and reloads dynamics into the existing map and opens the introduction; it does not call `CGame::Init` again.
- **Choose another standalone battle:** [MapSelection.cpp](../../MatrixGame/src/MapSelection.cpp) saves the choice and requests a relaunch. [WinMain](../../MatrixGame/src/MatrixGame.cpp) cleans up the old session and starts another process through the loading handshake.
- **Enter another hosted battle:** [MatrixGameDll.cpp](../../MatrixGame/src/MatrixGameDll.cpp) provides the x86 host entry boundary. Successful original-host reentry and borrowed resources remain HOST-01 evidence; closing the format/host implementation issue did not execute that native check.

This order is a delivery recommendation, not a new set of GitHub blocked-by relationships. A shared document or a preferred sequence is not a hard dependency.
