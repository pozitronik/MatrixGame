# Cheat registry and created robots

This inventory reconciles the twenty entries in `MatrixGame/src/cheats.cpp` with executable command evidence for C6/MODE-01. It supplements [player orders](player-orders.md) and the [baseline completion contract](baseline-completion.md). A parser assertion establishes the registered effect; movement, results, timing and camera behavior need the linked continuation cases. This inventory does not accept the complete behavior baseline.

The raw `Cheats::processInput` boundary is callable in both cheat configurations. It is not the game's compile-time admission gate. SPAWN, CRAZYBOT creation and deployment separately exercise the real `CFormMatrixGame::Keyboard` path: cheats-enabled builds perform the action, while disabled builds preserve the world and queue. Keyboard release is checked after delivery. The trailing-space and VIDEO cases deliberately use the raw parser, as identified above.

Debug F is outside this registry. `game.player.debug_building_reinforcement` targets a friendly, enemy or neutral synthetic factory with reinforcement enabled/disabled and a zero/positive cooldown. It presses and releases F through the real form. In Debug, F first clears the countdown; an eligible nonneutral building then requests the real transport, restores the 1000 ms cooldown, consumes three RNG draws and assigns its cargo an Attack group. Disabled or neutral buildings produce no transport. Release leaves the cooldown and world unchanged. This gate depends on `_DEBUG` without `_RELDEBUG`, independently of cheats. The carrier belongs to the building's side, but its robot cargo belongs to the player even for the enemy building. The test preserves this observed ownership quirk and advances the live carrier/cargo through the first 100 ms; complete landing/retirement is established separately by [reinforcement delivery](reinforcement-fixtures.md).

The optional `game.outcome.trace_result_callbacks` already covers generic Shift+Escape opening the menu in a matching trace build, separately from synthetic side-specific Shift result injection. The [trace guide](85-trace-results.md) explains why those side-specific codes are not native keyboard shortcuts.

## Creation, capacity and lifetime

The generated module meshes have explicit head, armor, weapon and exhaust attachment matrices, material-bearing skins and combat animations. The declared antigravity speed, rotation and surface corrections permit real movement on the synthetic landscape. Module prices are positive, so unchanged resource balances demonstrate that these cheat creation routes do not charge for construction. The fixture uses the production constructor and special-design assembly rather than inserting the resulting modules itself. It supplies synthetic resource data and an explicit unavailable-icon-render-target profile: the expected icon attempt fails with `D3DERR_NOTAVAILABLE`, not simulated successful rendering. Audio is unavailable and no window is created.

SPAWN creates a ready player robot at the supplied trace coordinates, with no base, a Stop group and 1000 displayed maximum health. Its four initialized laser effects, Dynamo head, chassis and armor are inspected before a production context Move travels more than 100 world units and reaches its destination. An ordered trace includes the shared world snapshot, created robot coordinates and health as raw float bits, side, state, crazy flag, group order/destination/target nullness and RNG draws. Each ordinary creation/Move and last-slot profile is repeated in a fresh Session and compared exactly within that build and RNG mode.

SPAWN bypasses the normal production unit ceiling: with 60 player robots occupying distinct slots 0 through 59, it creates a sixty-first robot in the final valid slot 60. This synchronous boundary is checked without advancing an over-limit side through unrelated fixed-size AI buffers. No graceful rejection is invented. A further spawn with all 61 logic-group slots occupied is outside the passing fixture: source inspection finds only `ASSERT(no < MAX_LOGIC_GROUP)` before the chosen slot is indexed. The exhausted-array path is a source-derived out-of-bounds hazard with [separate disposition and regression ownership under #80](../research/89-legacy-evidence/80-cheat-findings.md#exhausted-logic-group-slots); it is not a passing characterization or an executed defect probe. C6 remains incomplete pending that disposition and evidence.

CRAZYBOT needs a selected constructor base. With a base, its first six requests enter the actual build queue; the seventh preserves the queue, resource balances and icon-attempt count. Without a base no item is created. All accepted items retain their order and previous/next links, side, base, team zero, crazy flag, material-bearing modules and five initialized weapon effects: cannon, missile, mortar, laser and plasma. Queue destruction retires every retained object core. Creation alone grants no build statistic.

The deployment cases then put one actual CRAZYBOT order through a registered base's production ticks. They observe `ROBOT_IN_SPAWN`, opening, `ROBOT_BASE_MOVEOUT`, detachment beyond `BASE_DIST`, restored manual eligibility and closing. The crazy flag and design remain intact, balances are unchanged, and the build statistic remains zero: the crazy branch of `RobotSpawn` skips the normal statistic increment. The fixture keeps one friendly chassis and two enemies alive to prevent an unrelated outcome dialog during assembly. This is deployment evidence, not a balanced combat or crazy-target-selection golden.

Each deployment profile has its own CTest process because `CMatrixRobotAI::LogicTakt` retains `ppx`, `ppy` and `cnt` as function-static crazy-robot history. A second Session in the same process can choose a different target and group during the same deployment schedule; the new fixtures do not reset that production state. The cases print the number of observed frames and an FNV-1a digest of the complete ordered observation strings for fresh-process replay comparison. Fresh-process digest comparison is a manual validation step; no registered assertion compares these digests, so CI does not detect deployment replay divergence from this output alone. The digest is a replay aid, not an accepted historical reference or a cross-compiler equivalence claim. [Cross-battle crazy-history isolation remains a separate investigation owned by #80](../research/89-legacy-evidence/80-cheat-findings.md#cross-battle-crazy-history).

## Reproduction

Run the new registry and creation cases in both configurations, then repeat with `-Cheats` to check enabled form admission:

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.(cheats\.(diagnostic_registry|video_registry|hurry_boundaries)$|player\.(spawn_cheat_|crazy_cheat_|debug_building_reinforcement))'
.\tools\test.ps1 -Configuration Release -Filter '^game\.(cheats\.(diagnostic_registry|video_registry|hurry_boundaries)$|player\.(spawn_cheat_|crazy_cheat_|debug_building_reinforcement))'
```

Creation, deployment and Debug F use seed 80, both RNG modes and 10/16 ms scheduling. Discrete raw diagnostic/countdown effects do not advance simulation and need no timestep variant. Assertions remain active in Release. The ordinary CTest process limit and the shared Session frame/wall-clock bounds apply. These tests change no production source or host/resource ABI. Native rendering, original packages, accepted reference comparisons and complete-baseline integration remain separate validation requirements.
