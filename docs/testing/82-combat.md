# Combat firing, damage and lifetime contracts

These contracts implement part of [combat preservation](https://github.com/pozitronik/MatrixGame/issues/82). They exercise production damage handlers, weapon-hit callbacks and bounded armed full-map scenarios; they do not establish the complete COM-01, COM-02 or COM-03 behavior baseline. The source reference is `a64e9db4595bf06cc456772cb02c70f6a34b6804`, with scenario ownership defined by the [behavior catalog](../research/75-behavior-baseline/README.md). No production behavior or resource format changes are included.

## Running the tests

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.combat\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.combat\.'
```

The thirteen component CTest contracts link `MatrixGameInternal`, use `MG_CHECK` in every configuration and run in separate processes without an interactive window or supplied resource packages. Every contract runs with seed 82 in both Park-Miller and legacy CRT modes. The fixture is the existing `CommandWorld`, with engine-allocated objects and synthetic damage tables restored at teardown. No simulation frames are advanced: the schedule consists of the explicit damage/callback sequence in each case. This is component evidence, not a substitute for the controlled full-map scenario profile or its trace comparison.

The [static combat input catalog](static-combat-inputs.md) identifies the exact thirteen-case selection, shared literal inputs, source/body hashes, active assertions and unasserted limits.

Audio has no backend. Hit positions are deliberately far outside the default camera's effect distance, so production explosion culling prevents presentation assets from being loaded. Robot family cases also remain above zero and at or below 50 internal health units. Do not generalize their RNG consumption or lifetime evidence to visible explosions or a native device. The owner-retirement fixture supplies an identity-only core without mesh-derived bounds; it tests ownership and callback dispatch, not collision detection.

## Armed scenarios and reusable geometry

The armed contracts use the existing `Session` full-map boundary. Firing, repair and detonation scenarios run twice in the same process with seed 82 in each RNG mode, except the separately bounded heat variants; the two traces must match exactly. The laser scenario uses both 10 ms and 16 ms schedules. Plasma and turret scenarios use 10 ms. These are controlled profiles with a storage-only Direct3D surrogate, no native drawing and no audio backend. They do not establish equivalence with a packaged game's frame pacing or its rendering-dependent RNG consumption.

`battle_mesh.hpp` exposes `load_battle_mesh(attachments, cache_name, combat_animations)`. It writes a genuine storage-format box mesh, loads it through production `CVectorObject::LoadSpecial`, and removes its temporary file immediately. Each `MeshAttachment` provides a matrix ID, name and translation. The optional cache name makes a preloaded synthetic mesh available to production `LoadObject`; the optional animations add `Fire` and `FireLoop`. The original unarmed chassis uses the same box, frame and attachment values as before this extraction. Its implementation remains in `battle_geometry.cpp`, so existing targets need no additional mesh translation unit.

`BattleCombatAssets` must be constructed before `Session` and installed after it. It supplies two debris types, non-uploaded billboard texture handles and the plasma-impact and crater decal properties, and synthetic rocket/bullet/mine meshes. The session owns production effect teardown; the outer guard then restores the borrowed static catalogs. `arm_battle_robot` attaches synthetic armor and a weapon, invokes production `RobotWeaponInit` and `CalcRobotMass`, and updates real attachment transforms. All ten robot weapon kinds are supported and exercised, including the second attachment matrix required by repair. `create_battle_cannon` provides the basis/turret/shaft mesh chain expected by turret type 1; production `RNeed` creates the units, weapon, owner reference and firing callback. No targeting, collision, projectile, damage or cooling implementation is substituted.

Synthetic weapon settings are explicit in the test: range 600 for the robots, cooldown 100 ms, damage two, minimum-damage threshold ten, heat and cooling increments ten, and cooling period 100 ms. The turret uses range/seek radius 300 and its own angle limits. These values establish reproducible control-flow examples, not a balance baseline for packaged configuration. The no-draw billboard catalog uses synthetic intense texture handles; visual correctness and alternate effect catalogs are outside this profile.

Each run writes JSONL under the test executable's `scenario-traces` directory. The header records source revision and dirty state, compiler/configuration, assertion/cheat flags, floating-point mode, RNG and schedule. The header identifies the armed fixture and scenario; standard schema-1 snapshots add a `combat` object. Every boundary includes the session's robots/groups/RNG count, patient health bits, weapon heat while the shooter exists, and turret target/angle observations where applicable. Command records include acceptance, before/after RNG counts and the resulting group order; a completion footer follows the last snapshot. The files are accepted by `tools/compare-battle-traces.py`. Repeated runs report the first divergent boundary with both states. Fixed impact schedules and health assertions provide an oracle in addition to repeatability; two identically wrong runs are insufficient to pass those checks. The original laser, plasma and turret-retarget corpus also has a [dedicated real-file CI validator](82-combat-recordings.md), with its exact inventory, observation contract and reference limits.

## Additional weapon, repair and bomb scenarios

Nine further contracts cover the remaining robot weapon kinds, heat and cooling, real repair effects, and manual bomb detonation. They retain the same synthetic no-draw profile. Six family scenarios use a stationary patient, range 600, cooldown 500 ms and two internal damage units per normal impact. Ablaze/shorted health damage is explicitly zero in those family fixtures, so status effects still tick and consume RNG without obscuring the primary impact sequence. This separation does not establish secondary-damage arithmetic or timing; those are separate cases.

The table lists simulation milliseconds and internal health after each observed health transition. Multiple damage callbacks can occur within one boundary, so a transition is not necessarily a single shot. In particular, the gun fixture includes boundaries with four internal damage units. ## Modules, splash boundaries and chained explosions

`module_modifiers` builds all six armor kinds with all four head kinds under both RNG modes. It uses explicit synthetic text definitions for the four head names and calls production `RobotWeaponInit` and `CalcRobotMass`. The assertions cover total health, weapon range, heat increment, chassis speed, radar radius and electric/bomb/aim protection, including the lower -100% modifier clamp and protection clamping to [0, 1]. Geometry remains the same synthetic attachment chain across kinds; this is configuration arithmetic evidence, not validation of native armor/head models. Fixture-only module replacement releases the original weapon before reinitialization, preventing accidental accumulation of modifiers.

`module_firing` checks the resulting behavior through real attack orders. A neutral robot, a head with -50% cooldown, and one with +50% cooldown all first hit at 200 ms. Their later intervals are 100, 50 and 150 ms respectively, producing 19, 37 and 13 hits by 2000 ms and leaving the initially 100-health patient at 62, 26 and 74 internal units. Range is deliberately sufficient in all three variants, so moving into range does not obscure the cooldown comparison. Each case is replayed under both RNG modes.

`splash_boundary` derives an exact fixture boundary from the loaded patient's bounding sphere: center distance minus patient radius. A bomb radius equal to that distance, or one unit smaller, causes no damage. One unit larger causes exactly four friendly-fire damage units at 310 ms. This tests the production sphere enumeration's strict boundary, including its effect timing, with three separate replays per RNG mode.

`chained_bombs` places an enemy bomber between the manually detonated player bomber and a nearby armed player robot. The first blast kills the enemy bomber at 310 ms and reduces the nearby player's health from 10 to 6. The enemy's production danger evaluation triggers its own bomb; that blast kills the nearby player at 610 ms, leaving the observed internal health at -4. Each side receives one kill. Retained cores verify actual deletion of all three dying objects: 4080/4140 ms for the first bomber, 3140/4290 ms for the enemy bomber and 5520/4440 ms for the final victim, in Park-Miller/CRT order. The scenario continues to 6500 ms and is replayed under each RNG mode.

## Targeting, status refresh and difficulty

`repair_redirect` changes the player's repair order at 150 ms from one damaged friendly robot to another. The original patient is still repaired at 210 ms, after the redirected order: the effect retains and searches for its own eligible patient. The replacement receives repairs at 410, 510, 610, 710 and 810 ms. Once it reaches full health, the effect returns to the original patient at 1010, 1110 and 1210 ms. Both reach 50 internal health. This preserves the distinction between the logical order target and the repair effect's geometric patient selection.

`cannon_patient` sends real attack orders against synthetic cannon geometry. Its cannon at `(500,500)` reserves the existing navigation place at `(48,48)` before the order; the fixture checks the index and coordinates. A laser produces thirteen impacts at 200 through 1400 ms in 100 ms increments, leaving 24 internal health units. Plasma impacts at 1130, 1230, 1320, 1420, 1520, 1610, 1710, 1800, 1900 and 1990 ms leave 30 units. The cannon starts at 50 and remains under construction, preventing autonomous return fire. Both RNG modes replay each complete 2000 ms episode. These assertions cover production collision and cannon damage, not only direct calls to `Damage`.

The fixture identity is `synthetic-cannon-patient-navigation-v2`. The earlier setup left `m_Place` at `-1`, which the production attack command used to index the navigation array. AddressSanitizer detected the out-of-bounds read. Reserving the correct place changes destination allocation and therefore the firing journey; the former five-hit expectations came from an invalid setup and must not be treated as a compatible reference. The correction retains the seed, commands, 10 ms tick schedule and episode duration. It does not change navigation or combat rules in production.

`game.orders.pool_compaction` fills the real five-order pool with distinct phases and raw parameter bits, including negative zero and repeated object references. Head, middle, tail, final and invalid removals must preserve every surviving field, release exactly the removed reference and leave time and RNG unchanged. AddressSanitizer rejects the old overlapping `memcpy`; production now uses `memmove` with a trivially-copyable type assertion. Layouts, active-order ownership and execution order remain unchanged. Ordinary Debug/Release runs check the value and lifetime contract; the sanitizer distinguishes undefined overlapping copies even on CRT implementations that happen to preserve the bytes.

`robot_boundaries` uses stationary robots with the target 300 units ahead and 24 units sideways. Ranges of 300, 301.25 and 302 bracket the aim-point distance in this fixture: the first cannot hit; the latter two hit at 200 through 1000 ms in 100 ms steps. With hull rotation disabled, initial offsets of 13 and 17 degrees bracket the firing-angle limit while accounting for the synthetic muzzle offset: the first hits at 120 through 920 ms, and the latter never hits. This is a finite range/angle bracket, not an assertion that every native geometry has an exact 301-unit or 15-degree boundary.

`cannon_acquisition` derives the search boundary from center distance minus patient radius. One unit below and equality acquire no target; one unit above acquires at 110 ms and produces 17 hits beginning at 330 ms. Maximum rotation increments of 0.05 radians delay the first hit to 440 ms; the zero setting selects production's smooth rotation path and delays it to 880 ms. A separate upper-pitch limit of -1.2 radians permits 17 shots but no hits. Every step checks configured rotation limits; target acquisition, actual shots and damage are counted separately. Exported observations include both cannon body yaw and rotating turret yaw.

`status_refresh` reapplies fire or electric status ten milliseconds before expiry. Remaining lifetime is extended rather than replaced, and the next damage schedule restarts. Fire expires at 600 ms and leaves health 28 after eight nine-point bursts; electric status expires at 1000 ms and leaves health 60 after twenty two-point pulses. These cases verify expiry, health transitions and exact replay under both RNG modes.

`status_lethal` covers lethal first delayed callbacks, their attacking-side kill credit, dying state and physical removal. Before the correction for [#133](https://github.com/pozitronik/MatrixGame/issues/133), the first ablaze or shorted callback cleared the stored attacking side, so later callbacks lost kill credit and could switch friendly damage to the enemy-to-player multiplier. `delayed_status_attribution` runs the later-callback variants (fire reaches its second callback within the first 10 ms frame, electricity at 60 ms) and requires one hostile kill with unchanged dying and removal times, repeated for trace equality. `delayed_status_scaling` hits a stationary player robot once with each status from side 2 and from its own side, with unequal enemy/friendly table values (ablaze 4/3, shorted 6/5) and multipliers (enemy-to-player 2, friendly fire 0.5). Pulse timing does not depend on the side, so the enemy run's per-frame losses count pulses of 8 or 12, and the friendly run must lose exactly that many pulses of 1.5 or 2.5 in every frame. `delayed_status_attacker_retirement` removes the attacking side's robot after the hit; the later lethal callback still credits that side. Fire and electricity share one stored attacking side, so the most recent flame or electric hit owns every later pulse of both statuses. Before the correction only the first pulse after a hit carried an owner; now a shock by another side changes the kill credit and the damage table and multiplier of the remaining fire pulses. `delayed_status_mixed_owners` pins this rule in both RNG modes. On a player robot, a friendly flame followed by an enemy shock loses enemy-scaled pulses, and an enemy flame followed by a friendly shock loses friendly ones, in every frame. The kill credit follows the last owner: the enemy for the former, the player for an enemy robot lit by its own side and shocked by the player, and nobody for an enemy robot lit by the player and shocked by its own side. Separate sides per status would be a stacking redesign outside this correction. A direct hit by any other weapon still clears the stored side, as before; `delayed_status_direct_hit` applies a zero-damage gun hit after each status and requires that the later lethal pulse awards no kill. How direct hits should interact with active statuses is a separate decision. `delayed_status_original` selects the original attribution (`DelayedDamage=Original`, see [#154](https://github.com/pozitronik/MatrixGame/issues/154)) and requires the original outcomes: a later lethal callback awards no kill, and a friendly status costs one friendly pulse followed by enemy-scaled pulses. `turret_delayed_attribution` repeats the later-callback kill for an idle side-2 turret hit by the player, in both attribution modes, with the attacking robot removed after the hit and with a zero-damage gun hit after the status hit. Only the corrected mode without the gun hit credits the player with `STAT_TURRET_KILL`. `turret_delayed_scaling` applies the robot scaling check to a player turret in both modes: in the corrected mode every frame's friendly loss matches the enemy pulse count, and in the original mode the friendly total is one friendly pulse plus enemy-scaled pulses for the rest. It also counts RNG draws: enemy statuses draw the same in both modes, while a friendly fire status draws once more in the original mode for the player turret's under-attack voice, and a friendly electric status draws more. `turret_mixed_owners` applies the shared-owner rule to a player turret in both modes. In the corrected mode a friendly flame followed by an enemy shock loses enemy-scaled pulses in every frame, and the reverse loses friendly ones. In the original mode both orders end in hostile pulses after the first. A side-2 turret lit by its own side and shocked by the player is a player kill only in the corrected mode; one lit by the player and shocked by its own side is nobody's kill. Cases that expect the corrected attribution select it explicitly, because a DLL build starts in the original mode, and scenario trace headers record the mode as `delayed_damage`. `friendly_lethal` independently applies a lethal friendly gun hit and checks that neither side receives kill credit.

`friendly_difficulty` runs an actual bomb explosion against friendly geometry with effective friendly-fire multipliers 0, 0.5, 1 and 2. Resulting health is 50, 48, 46 and 42, with the nonzero hits at 310 ms. `cannon_difficulty` applies the same four enemy-to-player multipliers to autonomous laser fire. Each turret fires seven times; health ends at 50, 43, 36 and 22. Zero multipliers suppress damage without suppressing shots. These complement the component matrix across robot, building and cannon damage handlers.

`splash_boundary` and `friendly_difficulty` use separate recording contexts: `splash-boundary-*` and `friendly-difficulty-*`. Their offset-one, friendly-factor-one runs intentionally have identical gameplay inputs; separate names preserve both callers' recordings when CTest runs them concurrently. With both RNG modes and the existing replay ordinals, the two callers write 12 and 16 distinct files respectively. This naming distinction does not extend the dedicated laser/plasma/turret recording validator to these families.

## Building targets and complete demolition

`building_patient` integrates the reviewed synthetic building fixture with real player attack orders. It runs laser and plasma weapons against all six building kinds under both RNG modes, starting each target at 50 internal health units. The surviving enemy robot is stationary at (620, 620), and the target building is at (200, 200).
