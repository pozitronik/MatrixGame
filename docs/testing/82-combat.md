# Combat firing, damage and lifetime contracts

These contracts implement part of [combat preservation](https://github.com/pozitronik/MatrixGame/issues/82). They exercise production damage handlers, weapon-hit callbacks and bounded armed full-map scenarios; they do not establish the complete COM-01, COM-02 or COM-03 behavior baseline. The source reference is `a64e9db4595bf06cc456772cb02c70f6a34b6804`, with scenario ownership defined by the [behavior catalog](../research/75-behavior-baseline/README.md). No production behavior or resource format changes are included.

## Running the tests

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.combat\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.combat\.'
```

The thirteen component CTest contracts link `MatrixGameInternal`, use `MG_CHECK` in every configuration and run in separate processes without an interactive window or supplied resource packages. Every contract runs with seed 82 in both Park-Miller and legacy CRT modes. The fixture is the existing `CommandWorld`, with engine-allocated objects and synthetic damage tables restored at teardown. No simulation frames are advanced: the schedule consists of the explicit damage/callback sequence in each case. This is component evidence, not a substitute for the controlled full-map scenario profile or its trace comparison.

Audio has no backend. Hit positions are deliberately far outside the default camera's effect distance, so production explosion culling prevents presentation assets from being loaded. Robot family cases also remain above zero and at or below 50 internal health units. Do not generalize their RNG consumption or lifetime evidence to visible explosions or a native device. The owner-retirement fixture supplies an identity-only core without mesh-derived bounds; it tests ownership and callback dispatch, not collision detection.

The tests enumerate all seventeen explicitly. Fractional public health getters scale robot/building internal units by ten. Where an exact float result matters, assertions compare the returned binary32 representation, avoiding a comparison between an x87 extended temporary and a rounded float literal. ## Armed scenarios and reusable geometry

The armed contracts use the existing `Session` full-map boundary. Firing, repair and detonation scenarios run twice in the same process with seed 82 in each RNG mode, except the separately bounded heat variants; the two traces must match exactly. The laser scenario uses both 10 ms and 16 ms schedules. Plasma and turret scenarios use 10 ms. These are controlled profiles with a storage-only Direct3D surrogate, no native drawing and no audio backend. They do not establish equivalence with a packaged game's frame pacing or its rendering-dependent RNG consumption.

`battle_mesh.hpp` exposes `load_battle_mesh(attachments, cache_name, combat_animations)`. It writes a genuine storage-format box mesh, loads it through production `CVectorObject::LoadSpecial`, and removes its temporary file immediately. Each `MeshAttachment` provides a matrix ID, name and translation. The optional cache name makes a preloaded synthetic mesh available to production `LoadObject`; the optional animations add `Fire` and `FireLoop`. The original unarmed chassis uses the same box, frame and attachment values as before this extraction. Its implementation remains in `battle_geometry.cpp`, so existing targets need no additional mesh translation unit.

`BattleCombatAssets` must be constructed before `Session` and installed after it. It supplies two debris types, non-uploaded billboard texture handles and the plasma-impact and crater decal properties, and synthetic rocket/bullet/mine meshes. The session owns production effect teardown; the outer guard then restores the borrowed static catalogs. `arm_battle_robot` attaches synthetic armor and a weapon, invokes production `RobotWeaponInit` and `CalcRobotMass`, and updates real attachment transforms. All ten robot weapon kinds are supported and exercised, including the second attachment matrix required by repair. `create_battle_cannon` provides the basis/turret/shaft mesh chain expected by turret type 1; production `RNeed` creates the units, weapon, owner reference and firing callback. No targeting, collision, projectile, damage or cooling implementation is substituted.

Synthetic weapon settings are explicit in the test: range 600 for the robots, cooldown 100 ms, damage two, minimum-damage threshold ten, heat and cooling increments ten, and cooling period 100 ms. The turret uses range/seek radius 300 and its own angle limits. These values establish reproducible control-flow examples, not a balance baseline for packaged configuration. The no-draw billboard catalog uses synthetic intense texture handles; visual correctness and alternate effect catalogs are outside this profile.

Each run writes JSONL under the test executable's `scenario-traces` directory. The header records source revision and dirty state, compiler/configuration, assertion/cheat flags, floating-point mode, RNG and schedule. The header identifies the armed fixture and scenario; standard schema-1 snapshots add a `combat` object. Every boundary includes the session's robots/groups/RNG count, patient health bits, weapon heat while the shooter exists, and turret target/angle observations where applicable. Command records include acceptance, before/after RNG counts and the resulting group order; a completion footer follows the last snapshot. The files are accepted by `tools/compare-battle-traces.py`. Repeated runs report the first divergent boundary with both states. Fixed impact schedules and health assertions provide an oracle in addition to repeatability; two identically wrong runs are insufficient to pass those checks.

## Additional weapon, repair and bomb scenarios

Nine further contracts cover the remaining robot weapon kinds, heat and cooling, real repair effects, and manual bomb detonation. They retain the same synthetic no-draw profile. Six family scenarios use a stationary patient, range 600, cooldown 500 ms and two internal damage units per normal impact. Ablaze/shorted health damage is explicitly zero in those family fixtures, so status effects still tick and consume RNG without obscuring the primary impact sequence. This separation does not establish secondary-damage arithmetic or timing; those are separate cases.

The table lists simulation milliseconds and internal health after each observed health transition. Multiple damage callbacks can occur within one boundary, so a transition is not necessarily a single shot. In particular, the gun fixture includes boundaries with four internal damage units. Expectations record that result without merging it into the other weapon families.

`repair_firing` damages a friendly robot from 50 to 30 internal units, issues production `PGOrderRepair`, and observes actual repair-tool acquisition and effects. Four units are restored at 110, 210, 310, 410 and 510 ms. Health remains saturated through 2000 ms. The paired failure variant removes the patient at 300 ms: only the first two repairs occur, and by 400 ms the group target is null and the healer no longer has a firing order. Both variants are replayed in both RNG modes.

`heat_boundary` exercises the firing eligibility boundary using the existing maximum heat of 1000. A heat increment of 500 permits the equality case, then suppression and recovery with cooling increments of 100 every 100 ms. Real hits occur at 200, 790, 1380 and 1970 ms; the sampled maximum heat is 500. Increment 501 prevents the first shot, leaves heat at zero and preserves patient health. Both modes are checked. The 590 ms spacing is the observed combined weapon/robot schedule, not a test-side cooling simulation.

`bomb_detonation` invokes production `BigBoom` with radius 150. The bomber enters `ROBOT_DIP` on the next 10 ms boundary. Its friendly stationary neighbor loses exactly four internal health units at 310 ms; an enemy outside the radius remains unchanged, and neither side receives a robot-kill statistic for the self-destruction. A retained production core distinguishes death from deletion: the bomber's object disappears at 4080 ms with Park-Miller and 4140 ms with CRT. The scenario continues through 6010 ms and is replayed, exercising actual explosions, debris, callbacks and teardown. This is manual activation; the separate `bomb_order` contract below covers order-driven detonation.

## Turret projectile and boundary scenarios

`cannon_projectiles` adds the three non-laser turret weapon families. Each uses the existing synthetic three-part turret and its single muzzle, with range 300, cooldown 250 ms and a stationary robot patient at 50 internal health units. This tests the configured weapon implementations, not the native attachment layout of each turret model. The normal runs last 1000 ms; the destruction variants deal lethal production damage to the turret at 220 ms, after its first shot and before that shot hits, then continue through 6500 ms.

| Weapon | Normal impact time:remaining internal health | Impact after owner destruction | Actual owner removal, Park-Miller/CRT |
| --- | --- | --- | --- |
| `WEAPON_CANNON0` | 240:48, 490:46, 740:44, 990:42 | 240:48 | 3730/4730 ms |
| `WEAPON_CANNON1` | 250:46, 500:42, 750:38, 1000:34 | 250:46 | 3730/4730 ms |
| `WEAPON_CANNON3` | 520:48, 770:46 | 520:48 | 4250/4010 ms |

The destruction variants assert entry into `CANNON_DIP`, exactly one player turret-kill statistic and eventual clearing of a retained production object core. They preserve the observed multiple damage callbacks for `WEAPON_CANNON1`. No extra hits may occur after the one in-flight shot. Every normal and destruction variant is replayed under each RNG mode.

`cannon_boundaries` derives the squared distance from the loaded turret and patient centers. It finds the first representable radius whose squared value passes the production comparison, then tests that radius and its immediate float32 neighbors. The smaller neighbor allows acquisition and aiming but no shot. The eligible radius and its larger neighbor produce seven laser hits, at 330 through 930 ms in 100 ms steps. Two additional variants restrict the lower pitch angle: zero radians prevents firing; -0.5 radians allows seven shots but no damage because the beam misses the synthetic patient. Every boundary also checks angle limits, retained target identity, final health and same-profile replay. Acquiring a target, firing and hitting therefore have separate assertions.

`cannon_obstruction` places an inert, under-construction turret between the attacker and its patient. The attacker has no target while obstructed. Removing the obstruction at 500 ms through production `StaticDelete` permits reacquisition and hits at 660, 760, 860 and 960 ms. The unobstructed control hits at 220 through 920 ms, while an attacker initially under construction never acquires a target or damages the patient. These are initial-state and obstacle-removal tests; they do not claim to exercise construction completion. All three variants are replayed in both RNG modes.

## Timed damage and robot lifecycle scenarios

`delayed_damage` applies real zero-damage flame/electrical hits to a stationary robot with 100 internal health, then advances the complete map. Ablaze lasts 300 ms and deals nine internal units at 10, 100, 190 and 280 ms, ending at 64 health. Shorting lasts 500 ms and deals two units at 10 through 460 ms in 50 ms steps, ending at 80. The combined variant preserves both schedules, ending at 44. Every 10 ms boundary checks the remaining status lifetime and active flags, and the run continues to 1000 ms to exclude damage after expiry. Exported combat observations now include status lifetimes and robot state. The test observer calls existing protected getters through base member pointers; it does not cast production objects to a test-derived type or alter their layout.

`bomb_order` issues production `PGOrderBomb` against a stationary enemy or the ground position (500, 500). The selected bomber navigates through the synthetic map and detonates through the order-processing path. The target-order variant enters `ROBOT_DIP` at 7920 ms and damages its patient from 50 to 40 internal health at 8210 ms. The ground-order variant reaches its destination later: death begins at 11820 ms and damage occurs at 12110 ms. Actual object removal follows the dying transition by 3150 ms under Park-Miller or 4140 ms under CRT. Each run continues to 30000 ms and asserts no robot-kill statistic for either side. This complements manual detonation; it does not claim to exercise the interface's bomb-button dispatch.

`repair_death` begins with the same real repair order as `repair_firing`, then deals lethal damage at 300 ms to either the healer or patient, after two successful repairs. A surviving patient remains at 38 health; a surviving healer loses its target and firing order by 410 ms. The attacking side receives exactly one robot-kill statistic. Patient removal occurs at 3980/2810 ms, and healer removal at 4780/3460 ms, for Park-Miller/CRT. Retained cores distinguish dying animation from actual destruction, and all runs continue through 6500 ms. These scenarios, status combinations and both bomb-order variants are replayed under each RNG mode.

## Modules, splash boundaries and chained explosions

`module_modifiers` builds all six armor kinds with all four head kinds under both RNG modes. It uses explicit synthetic text definitions for the four head names and calls production `RobotWeaponInit` and `CalcRobotMass`. The assertions cover total health, weapon range, heat increment, chassis speed, radar radius and electric/bomb/aim protection, including the lower -100% modifier clamp and protection clamping to [0, 1]. Geometry remains the same synthetic attachment chain across kinds; this is configuration arithmetic evidence, not validation of native armor/head models. Fixture-only module replacement releases the original weapon before reinitialization, preventing accidental accumulation of modifiers.

`module_firing` checks the resulting behavior through real attack orders. A neutral robot, a head with -50% cooldown, and one with +50% cooldown all first hit at 200 ms. Their later intervals are 100, 50 and 150 ms respectively, producing 19, 37 and 13 hits by 2000 ms and leaving the initially 100-health patient at 62, 26 and 74 internal units. Range is deliberately sufficient in all three variants, so moving into range does not obscure the cooldown comparison. Each case is replayed under both RNG modes.

`splash_boundary` derives an exact fixture boundary from the loaded patient's bounding sphere: center distance minus patient radius. A bomb radius equal to that distance, or one unit smaller, causes no damage. One unit larger causes exactly four friendly-fire damage units at 310 ms. This tests the production sphere enumeration's strict boundary, including its effect timing, with three separate replays per RNG mode.

`chained_bombs` places an enemy bomber between the manually detonated player bomber and a nearby armed player robot. The first blast kills the enemy bomber at 310 ms and reduces the nearby player's health from 10 to 6. The enemy's production danger evaluation triggers its own bomb; that blast kills the nearby player at 610 ms, leaving the observed internal health at -4. Each side receives one kill. Retained cores verify actual deletion of all three dying objects: 4080/4140 ms for the first bomber, 3140/4290 ms for the enemy bomber and 5520/4440 ms for the final victim, in Park-Miller/CRT order. An additional distant fixture robot outside the Session entity IDs keeps the player side alive so that this combat contract does not enter the mission-outcome interface; its health and the distant enemy observer's health remain unchanged. The scenario continues to 6500 ms and is replayed under each RNG mode.

## Targeting, status refresh and difficulty

`repair_redirect` changes the player's repair order at 150 ms from one damaged friendly robot to another. The original patient is still repaired at 210 ms, after the redirected order: the effect retains and searches for its own eligible patient. The replacement receives repairs at 410, 510, 610, 710 and 810 ms. Once it reaches full health, the effect returns to the original patient at 1010, 1110 and 1210 ms. Both reach 50 internal health. This preserves the distinction between the logical order target and the repair effect's geometric patient selection.

`cannon_patient` sends real attack orders against synthetic cannon geometry. A laser produces five impacts at 200 through 600 ms; plasma produces impacts at 1130, 1220, 1320, 1430 and 1530 ms. The cannon remains under construction, preventing autonomous return fire, and its health falls from 50 to 40. The assertions cover production collision and cannon damage, not only direct calls to `Damage`.

`robot_boundaries` uses stationary robots with the target 300 units ahead and 24 units sideways. Ranges of 300, 301.25 and 302 bracket the aim-point distance in this fixture: the first cannot hit; the latter two hit at 200 through 1000 ms in 100 ms steps. With hull rotation disabled, initial offsets of 13 and 17 degrees bracket the firing-angle limit while accounting for the synthetic muzzle offset: the first hits at 120 through 920 ms, and the latter never hits. This is a finite range/angle bracket, not an assertion that every native geometry has an exact 301-unit or 15-degree boundary.

`cannon_acquisition` derives the search boundary from center distance minus patient radius. One unit below and equality acquire no target; one unit above acquires at 110 ms and produces 17 hits beginning at 330 ms. Maximum rotation increments of 0.05 radians delay the first hit to 440 ms; the zero setting selects production's smooth rotation path and delays it to 880 ms. A separate upper-pitch limit of -1.2 radians permits 17 shots but no hits. Every step checks configured rotation limits; target acquisition, actual shots and damage are counted separately. Exported observations include both cannon body yaw and rotating turret yaw.

`status_refresh` reapplies fire or electric status ten milliseconds before expiry. Remaining lifetime is extended rather than replaced, and the next damage schedule restarts. Fire expires at 600 ms and leaves health 28 after eight nine-point bursts; electric status expires at 1000 ms and leaves health 60 after twenty two-point pulses. These cases verify expiry, health transitions and exact replay under both RNG modes.

`status_lethal` records an observed legacy statistics quirk. The first delayed damage callback can credit the original attacking side, but it also clears the stored attacker identity. A robot needing a later delayed callback dies without crediting that side. Fire's repeated callbacks can reach this case within the same 10 ms frame; electricity reaches it at the next pulse, 60 ms. Retained cores verify physical removal as well as the dying state. This is characterization of existing behavior, not endorsement of the attribution rule; changing kill credit requires a separate gameplay/statistics decision.

`friendly_difficulty` runs an actual bomb explosion against friendly geometry with effective friendly-fire multipliers 0, 0.5, 1 and 2. Resulting health is 50, 48, 46 and 42, with the nonzero hits at 310 ms. `cannon_difficulty` applies the same four enemy-to-player multipliers to autonomous laser fire. Each turret fires seven times; health ends at 50, 43, 36 and 22. Zero multipliers suppress damage without suppressing shots. These complement the component matrix across robot, building and cannon damage handlers.

## Remaining acceptance work

COM-01 has component evidence for all seventeen damage-table entries across robot, building and cannon targets; all ten robot weapon kinds also have production weapon/effect evidence against robots. Bounded scenarios add cannon-target laser/plasma hits, armor/head arithmetic and cooldown behavior, geometric range/angle and splash boundaries, obstruction, target/shooter removal, repair redirection, status refresh/lethality and effective difficulty variants. This does not establish a complete cross-product of native target shapes and trajectories. Building-target firing requires integration of the separately reviewed synthetic building fixture; native attachment layouts and packaged balance/resource behavior require the corresponding resource-backed validation. No gameplay extraction or production seam is justified by these gaps.

COM-02 covers damage, repair, bomb arrival/manual activation, chained damage, dying states, actual removal, retained cores and death during repair. Spawn/base-exit, capture interruption and direct-control restoration intersect the production, command and navigation scenarios; they must be validated at the reviewed shared-fixture integration boundary. Building explosion/removal and dependent robot deaths likewise need that building integration. The component building test proves only the immediate lethal transition.

COM-03 covers autonomous acquisition, lower and upper pitch, bounded rotation, firing and search range boundaries, all four turret weapon families, replacement targets, obstruction/reacquisition, under-construction suppression, difficulty and destruction with live projectiles. Construction completion belongs to the integrated production lifecycle; the synthetic attachment chain does not validate native turret assets or presentation.

These remaining integration and native-resource requirements retain their catalog ownership and block complete-baseline acceptance. The tests do not authorize a gameplay change or structural extraction. Windows x86 host DLL and MSVC configurations need their CI results; local MinGW checks alone do not establish those profiles.
