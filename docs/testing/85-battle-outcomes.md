# Capture and battle outcome characterization

The `game.outcome.*` suite adds production-backed checks for capture arithmetic, income ownership, battle results, pause and repeated synthetic sessions. It reuses the [controlled battle harness](../TESTING.md#controlled-battle-scenarios) and makes no production changes. The [behavior catalog](../research/75-behavior-baseline/README.md) remains the complete acceptance contract; the gaps below prevent treating this increment as a finished outcome baseline. The [outcome completion plan](85-outcome-completion.md) reconciles existing evidence and proposes the finite remaining selection, shared ownership and native handoff. It is a plan for review, not evidence that those scenarios pass. Its [schedule inventory](85-outcome-completion.md#existing-schedule-extensions) assigns missing 16 ms profiles to implementation rows; existing 10 ms evidence alone does not close them.

## Running the checks

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.outcome\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.outcome\.'
```

Assertions remain active in Release. The shared fixture bounds map advancement and restores its declared globals; CTest bounds each process. Debug additionally rejects leaked tracked allocations. The normal CI matrix supplies the MSVC and DLL build variants. These tests run without external resources or a native window.

## Capture boundaries

`neutral_capture`, `enemy_capture`, `capture_rejection` and `capture_rollback` invoke the actual `CMatrixBuilding::Capture` and, where required, `LogicTakt`. The nearby capturing robot has the shared fixture's real generated mesh and map membership; distance eligibility goes through production `FindObjects`, not a substituted answer. Side colors, the building's original ownership/color and its titanium income period are explicit initial data. Neutral and enemy capture each run independently under ParkMiller and LegacyCRT with seed 79.

In the direct capture cases, the building is a component fixture rather than an object scheduled by the map: the test owns it and supplies its capture and logic calls explicitly. Its automatic capture-search timer is deferred and its capturer marker is initialized, so those independently scheduled acquisition paths cannot add calls to a boundary test. The scheduled cases below enable the nearest-robot scanner explicitly. The separate registered-building cases below cover the command and approach path. No unit orders or capture results are written to obtain the expected transition.

With the default 750 ms erase and 500 ms paint periods, neutral capture at time zero is busy. The first point appears at 10 ms; equality at 500 ms remains busy and the next point appears at 510 ms. Fourteen painted points at 6,510 ms still leave the building neutral; ownership changes on the subsequent 7,010 ms call. Enemy capture keeps the old owner when its final colored point is erased at 9,760 ms, then neutralizes the building at 10,510 ms before repainting. Assertions distinguish count/color changes from ownership changes rather than treating a fully painted or erased bar as the completed transition.

Income checks call the real building logic at 999 ms and one further millisecond with a 1,000 ms period. Only the new owner receives titanium. The neutral interval in enemy capture does not pay the previous owner. These are component timing checks, not an income replay across the complete capture journey.

Rejection checks pass the farther friendly robot to the actual distance search, confirm no paint, then let the eligible robot paint. A second call at the same boundary is busy. Rollback checks stop calling `Capture`, exhaust its 1,250 ms keep-alive interval through building logic, verify that equality with the rollback clock does nothing, and advance the real map clock before checking removal of the point. The deliberately supplied building elapsed intervals isolate timeout arithmetic; they do not represent normal full-map scheduling or the production death/interruption route.

`competing_capturers` places both friendly robots inside the capture radius and checks that the farther caller cannot paint while the closer one can. `competing_color` starts with two points painted by the other side on a neutral building. It asserts each erase threshold, retains the old color until the erase operation finishes, then observes the erase clock continuing to gate entry while the paint loop catches up two points. These are distinct from combat or movement between rival capturers.

`scheduled_capture` runs complete map ticks followed by the component building's `LogicTakt` on the same 10 or 16 ms schedule. The building's real nearest-robot scanner calls `Capture`; the test never supplies that call. Under both RNG modes the first paint appears at 120/128 ms and ownership changes at 7,050/7,072 ms respectively. The initialized capturer marker suppresses the separate publication of capture candidates to nearby robots; it does not supply the scanner's nearest target. This exercises component acquisition scheduling, not the map's registered-building dispatch or robot approach order.

`acquisition_after_removal` deletes the scanner's nearest robot after two painted points. With another robot inside the radius the scan finds that survivor and completes capture; without one, timeout and rollback remove all paint. The fixture's separate capturer marker is kept on a live object solely to suppress candidate publication. Deletion uses the session's normal object retirement and bypasses combat/death animations. `enemy_capture_rollback` checks the opposite rollback direction: an interrupted erase restores the enemy's missing point and keeps its ownership and color.

`capture_queue_refund` supplies two queued enemy robots with real wheel-chassis units and explicit prices. The production base capture keeps its queue through the final erased point, clears it on neutralization, destroys the queued objects and refunds each of the four resources to the original owner exactly once. Subsequent player capture adds no further refund. The queue owns the unregistered robots; no queue timer, production deployment or building graphics runs in this component case.

`protected_base_command` registers a synthetic base and protecting turret in the real logic list and makes the turret known to a selected robot's enemy list as initial data. A context capture command retains capture intent but enters war without assigning a capture order. Deleting the turret through its normal destructor decrements the parent's protection count; reissuing the command assigns exactly one capturing robot. The form's S key cancels that order without changing the base's owner or paint. Both RNG modes run independently. The building and turret have no rendered geometry, and no map tick is run while they are registered; this establishes command assignment/cancellation, not approach, combat or completed base capture.

## Registered buildings and capture lifecycle

The [capture timing profiles](85-capture-profiles.md) extend the base journey, its keyboard/button routes, capture target removal and candidate lifetime, capturer death, base interruption and target damage to both 10 ms and 16 ms. Unless a separate schedule is stated, the capture lifecycle timings below describe the retained 10 ms profile; the supplement gives the independently measured 16 ms transitions and their preceding-tick assertions.

The registered-building cases use the reviewed [synthetic building fixture](building-fixtures.md) and complete `Session::advance` map ticks, including ordinary robot commands, candidate publication, building logic, side AI and side elimination. The initial logic list follows `MatrixMapPrepare.cpp`: buildings precede the buffered starting robots. This order matters to current `TaktPL` capture validation, whose scan can stop at an existing capturer before visiting a later building. These cases characterize the normal loaded-map ordering; arbitrary insertion order remains outside their contract. Resource periods are explicitly 100,000 ms, beyond these bounded runs; this both keeps income billboards outside the no-texture fixture and supplies valid divisors to enemy base production planning. Audio is unavailable in this profile, separately from the earlier audio-enabled component cases.

`registered_capture` and `registered_enemy_capture` send a context capture command to a titanium factory at (160,200). Exactly one selected robot receives the capture order. The map then runs without injected capture calls or ownership changes until acquisition completes, and a further second checks retained ownership and order cleanup. Both RNG modes run with independent 10/16 ms schedules. First paint or erase occurs at 630/640 ms. A neutral factory transfers ownership at 7,530/7,536 ms. An enemy factory neutralizes at 11,030/11,040 ms and transfers to the player at 18,540/18,544 ms. Exact assertions distinguish these transitions and require the final player color and all fourteen painted points. Opponent AI remains enabled and receives candidates normally; these unarmed robots do not establish contested combat capture.

`registered_base_capture` exercises neutral and enemy bases at (100,100) under both RNG modes. The real command takes the capturer through approach, opening, entry, closing and consumption: the base first opens at 1,280 ms, starts closing at 4,330 ms and changes ownership at 5,580 ms on the 10 ms schedule. The capturing robot stays alive until that transfer and then disappears through production deletion; the other player robot survives. The capturer marker clears and the base remains closed and player-owned afterward. The enemy variant starts with two queued chassis whose construction period exceeds the scenario duration. Both stay queued until capture; transfer clears the queue and refunds all four resource prices to their original side, leaving player balances unchanged. These are queue-owned chassis with declared costs, not constructor-assembled robots or production deployment.

`capture_candidate_lifetime` lets a registered neutral factory publish candidates through its normal map tick. A held production core reference observes three additional references from nearby robots; the next publication does not duplicate them. The manual player robot receives the informed marker but does not automatically take a capture order. Removing the building releases candidate ownership and leaves only the test's held reference, with a null object; a subsequent tick retains live robots without a stale capture target. This observes reference ownership, not the private candidate countdown values. `capture_target_removal` deletes the target after 200 ms of an actual approach: the robot's capture target/order clear immediately and its group reaches Stop with a null target by 400 ms. Both use production deletion, not damage or ruin construction.

`base_survival` removes a side's last robots while its registered base remains. Player and enemy sides both stay active across two status scans. Deleting that final base then produces elimination on the next scan at 4,030 ms and the appropriate paused result at 6,040 ms. Conversely, `factory_does_not_prevent_elimination` leaves only a titanium factory: the first scan eliminates the side, neutralizes the factory and clears its capture color; the next scan opens the result at 2,020 ms. Both RNG modes and both player/enemy cases run. These distinguish a surviving base from an ordinary resource factory without claiming combat destruction, remaining turret/flyer variants or special-map rules.

## Capture interruption and surviving turrets

`capture_combat_death` starts a registered factory capture through the ordinary context command, then applies lethal production laser damage to the capturer at 1,000 ms, after one point has been painted. `Damage` immediately enters `ROBOT_DIP`, releases the capture marker and awards the enemy exactly one robot kill. The surviving selected robot is assigned at 1,020 ms and completes capture at 7,530 ms; ownership, all fourteen points and the player's paint colour are asserted. A retained production core clears at 5,430 ms with Park-Miller and 4,110 ms with LegacyCRT, distinguishing dying from deletion. The scenario continues through 11,000 ms and repeats in each mode, comparing every map boundary, building ownership/progress and core presence. The damage call is scheduled directly; this contract does not add a firing attacker or test contested weapon aiming.

`base_capture_interruption` presses the form's Stop key during opening at 200 ms, entry with the base open at 2,000 ms, and closing at 4,500 ms. Each case checks the exact initial base state, capture assignment and manual-control flag. Stop clears the capture order and marker immediately. During opening it preserves the robot; during entry or closing, production `BreakAllOrders` marks the robot to die because manual control has already been disabled. Through 10,000 ms the base remains neutral and returns to its closed state; the second friendly robot survives, and neither side receives kill credit. Every variant repeats under both RNG modes and compares the full per-frame session state, base state and marker presence. This characterizes the existing cancellation behavior rather than changing it to preserve the entering robot.

These death scenarios reuse synthetic combat debris and billboards and provide a scoped crater-effect definition. Production explosions, unit death, capture cleanup and object removal run normally; the fixture restores the borrowed crater catalog after the session has retired its effects. No rendering or audio timing is established.

`turret_does_not_prevent_elimination` retains a real synthetic turret after removing its side's last robots. Both an active turret with a one-unit seek radius and a turret under construction are checked, for both sides and RNG modes. The turret remains live and keeps its owner, but it does not keep the side active: the first scan eliminates that side and the result opens at 2,020 ms. This tests the production distinction between robots/bases and turrets, not turret combat or construction completion. Transport flyer and cargo outcome boundaries are covered below.

`capture_target_damage` destroys the commanded target during factory painting at 1,000 ms or base entry at 2,000 ms. The lethal hit goes through production building `Damage`, which clears the robot's capture order immediately. The next player-group update clears the target and leaves Stop; the [capture timing supplement](85-capture-profiles.md) records the different 10/16 ms boundaries. A factory capturer survives; a robot already associated with the entering base has its base reference cleared and is marked to die by `ReleaseMe`. Both paths then run through real explosions, material-backed ruin creation and deletion: the factory's retained core clears at 2,010 ms, the base's at 5,010 ms. The enemy receives one building kill and no robot kill. The scenario continues through 10,000 ms with a surviving friendly robot and repeats in both RNG modes. The base's final blast has zero configured damage, separating its dependent robot death from area damage.

## Destructible map objectives

The timing descriptions below retain the original 10 ms profile. The [special-object timing guide](85-special-profiles.md) records the 10 ms and 16 ms coverage, measured conversion/result boundaries and remaining special-object scenarios.

`special_break`, `special_explosion` and `special_animation` load synthetic object descriptors through production `CMatrixMapObject::Init` and run the resulting special-object rules. Two objectives begin at ten health each. An enemy-side hit is rejected without allocating a progress bar or consuming RNG; a player hit reduces health to five. A second hit at the configured minimum threshold of five leaves health unchanged. Lowering the configured threshold to four allows the lethal hit at exactly zero. The destroyed object removes its special marker, decrements the objective counter once and awards one building kill.

The Break variants replace their type with a static object. The lethal-hit boundary asserts that the Explode variant adds production effects and that the non-explosive Break and Anim variants do not. The Anim variant follows its descriptor to animation state one and changes zero configured health to the engine's two-billion sentinel. Generated material-bearing box geometry and managed CPU textures support ordinary graph and skin loading; the test does not claim native artwork or visible animation fidelity. The explosion variant supplies the same scoped crater catalog as robot death.

After the first objective falls, removing the enemy army still produces no victory because one objective remains. Destroying the last objective sets `MMFLAG_SPECIAL_BROKEN` and `SS_JUST_WIN`, and repeated damage cannot decrement the objective count or award another kill. Removing every player robot afterward does not reverse the earned outcome: the next status decision retains victory, and the win dialog opens at 6,040 ms. Both RNG modes repeat their complete post-objective map-state sequence exactly. The descriptors, threshold configuration and hit calls are synthetic initial conditions and scheduled inputs; production parsing, state changes, counters, effects and outcome evaluation are used directly.

These cases cover Break and Anim objective families. The older `special_survival_flags` case remains useful as an isolated flag boundary but is not the evidence for destruction itself.

## Terron destruction

`terron_destruction` loads a synthetic Terron descriptor and actual named Main/Pain/Death animation records. Enemy damage leaves health, progress-bar ownership and RNG consumption unchanged. Player damage lowers health from ten to six and selects Pain; the lethal hit selects Death, removes the progress bar and sets the Terron-dead flag. Repeated hits immediately after death and at 2,000 ms leave RNG consumption, Death animation, zero health and the objective count unchanged; the later hit must not restart the countdown. Complete production map ticks then keep the objective active at exactly 5,000 ms, convert it to static ruins at 5,010 ms, decrement the objective count and award one building kill. The result remains pending at 8,040 ms and opens the paused win dialog at 8,050 ms. These values describe the 10 ms schedule; both RNG modes also run an independent 16 ms schedule with seed 85. Each profile retains or removes the player army immediately after the lethal hit; the latter verifies that Terron's death suppresses ordinary elimination.

The synthetic objective is at (600,100), with a blast radius of 20 and cooldown of 100 ms. This isolates the death/outcome sequence from collateral damage. Animation records each contain one synthetic frame; explosion effects advance but no image or sound is rendered. The [special-object timing profiles](85-special-profiles.md) also describe the independent 16 ms schedule and its exact conversion/result boundaries.

`game.outcome.terron_blast_after_conversion` puts the objective at (400,100) with radius 150 and observes damage after its conversion to static ruins. It replaces the unregistered probe for [#186](https://github.com/pozitronik/MatrixGame/issues/186). The former Debug check stopped because the valid owner had left the logic list; the correction also validates map ownership without changing Release behavior. Both RNG modes, both schedules, retained/removed player armies and nonlethal/lethal blast damage have assertions for affected robots, neutral kill attribution, exact RNG draws and the eventual win dialog. The [Terron blast regression](186-terron-owner.md) records the pre-fix Release reference and reproduction commands.

## Result and pause boundaries

`victory`, `defeat` and `simultaneous_loss` delete the relevant registered robots through the shared fixture and run the complete `CMatrixMapLogic::Takt`. Deletion bypasses damage and dying animations; the tests establish the subsequent live-entity outcome evaluation. They assert the player's side status, the win flag, the delayed dialog identity, pause ownership and absence of premature exit. Simultaneous loss follows the player-death branch and produces defeat.

The status scheduler compares `now - previous > 1001` but then stores `previous = now + 1001`. Consequently the first result check at 10 ms is followed by the dialog at 2,020 ms in this profile. Tests assert that no result dialog is present at 2,010 ms. The separately executed 16 ms profile stays dialog-free at 2,016 ms and enters the result at 2,032 ms. Victory, defeat, simultaneous loss and isolated full-auto results run in both profiles and both RNG modes. This preserves the observed interval despite the source comment describing a once-per-second check.

Dialog setup uses an actual empty `CInterface`, owned by the normal interface list, plus an empty template block. Production dialog state, pause and teardown therefore execute without loading artwork. No confirmation button or rendered hint is created: opening and leaving a dialog do not prove its confirmation callback, statistics screen or visible appearance.

`automatic_results` supplies `MMFLAG_FULLAUTO` and verifies exit state 1 and loop termination for both victory and defeat, with no result dialog or pause. `full_auto_escape` exercises Escape through the form under that same flag. These cases isolate full-auto result routing. They do not set `MMFLAG_AUTOMATIC_MODE`, construct a demo map or prove that complete high-level player AI and flying-camera startup work together.

`special_survival_flags` supplies each of `MMFLAG_TERRON_DEAD` and `MMFLAG_SPECIAL_BROKEN` as initial conditions, removes both player robots and verifies that ordinary side elimination is suppressed. It does not exercise the earlier Terron/special-object destruction that produces these flags or establish the complete special-map victory sequence.

`pause_resume` moves through the production command route, pauses using the form's Pause key, and checks that robot position, simulation time and reinforcement cooldown remain unchanged while paused. It resumes, verifies the first clock/cooldown decrement and requires arrival. Both RNG modes and the separate 10/16 ms profiles run independently. The suite does not infer that presentation, audio, camera or RNG activity stops merely because these gameplay clocks stop.

`paused_orders` verifies that pausing does not disable command entry: a move can be issued, stopped and replaced while the clock and position remain fixed, and the replacement executes after resume. `pending_result_pause` pauses just before the result deadline, verifies that repeated paused ticks do not reach it, then resumes into the expected result dialog. Escape does not dismiss that result. `pending_result_late_elimination` removes the other army after the first status decision; the already scheduled result keeps its original win/loss identity. This differs from `simultaneous_loss`, where both armies disappear before that decision.

## Statistics, cheats and repeated sessions

Side statistics use `timeGetTime`, independently of the fixed simulation clock. Defeat checks verify that the eliminated player's recorded time stays frozen. Victory checks bracket the final tick with native clock reads and verify that the stored negated duration lies inside that observed interval, including unsigned clock arithmetic. This establishes the sign-changing result operation without claiming a deterministic numeric timestamp. Exact reference traces for statistics still need an agreed clock-observation policy or a separately reviewed clock seam.

`statistics_formatting` starts at the normal or diagnostic statistics-request flag with explicit side counters. The complete map tick formats all five counters, side-name prefixes, hours/minutes/seconds and green winner markup, consumes the request and opens the correct paused statistics dialog without advancing simulation time or exiting. It also preserves two formatting edge cases: a zero time clears only the time replacement, leaving previously formatted counters, and a negative duration shorter than one second loses the winner markup after integer division. The empty templates provide no confirmation button; this test does not substitute the static result callbacks or prove the final Enter-to-exit route.

`legacy_loss_cheat` feeds IAMLOOSER through the production cheat parser. It preserves exit state 3, the win dialog, paused play, an unchanged statistics time and an unset `MMFLAG_WIN`. It calls the parser directly in either compiled variant; enabled/disabled keyboard dispatch is a different command-suite contract. The `legacy_loss_confirmation` continuation below now follows this parser result through confirmation, statistics and the exit request; it does not establish typed dispatch.

`repeated_sessions` alternates full-auto win/loss outcomes and constructs fresh synthetic sessions in the same process. It asserts cleared engine globals/live objects, fresh clocks, default selection/group membership, active player status and no carried pause or loop-exit flag. This tests the shared fixture's declared ownership and the production objects it owns. It does not exercise `CGame::Init` on a loaded map, the restart menu or arbitrary process-global startup/teardown.

## Transport and cargo outcome boundaries

The transport timing prose below describes the original 10 ms profile. The [survival and transport schedule guide](85-survival-profiles.md) records the independent 10/16 ms assertions in both RNG modes, including the base, factory and turret survival cases.

Six contracts use the shared synthetic transport body and robot assembly through real `OrderFlyer` and `ApplyOrder`. The fixture selects the existing unavailable-icon-target path; no artwork is loaded and no native rendering claim is made. The original profile used seed 85, a 10 ms map step and both RNG modes; the linked supplement records the separate 16 ms schedules. Empty result templates retain the same confirmation limitation as the other outcome contracts.

`flyer_does_not_prevent_elimination` schedules removal of the delivered robot before the first map tick, then removes the carrier owner's ordinary robots. Both player and enemy carriers continue flying, but neither keeps its side active: the first scan eliminates the side and the result appears at 2,020 ms. A call to the enemy side's `OrderFlyer` still constructs player-owned cargo because `ApplyOrder(FO_GIVE_BOT)` supplies `PLAYER_SIDE` explicitly. The test records that ownership and removes the cargo before checking empty-carrier survival; it does not claim enemy reinforcement delivery.

`transported_robot_prevents_elimination` leaves the newly assembled cargo as the player's only robot. The side stays active through carrying, falling, landing and carrier retirement. These profiles contain status scans during carrying and after landing, but none during the 320 ms fall; they do not isolate the falling robot's contribution to the survival predicate. This follows the production live-robot predicate, which excludes dying robots but includes carried and falling states. Every map boundary through 20,000 ms must remain free of defeat, victory and result pause. ParkMiller releases at 6,100 ms, lands at 6,420 ms and retires the carrier at 11,960 ms; LegacyCRT follows the same transitions at 4,940, 5,260 and 9,670 ms. These are seed-85 direct-order expectations, independently characterized from the seed-83 maintenance-request profile.

`transported_robot_removal` deletes the last robot at 1,000 ms while attached, or at 7,000 ms after landing. The production destructor clears the carrier link. The still-flying carrier cannot keep the player alive: the next scheduled status scan eliminates the player at 2,020 or 8,050 ms, respectively, and the following scan opens defeat. Direct removal awards neither side a robot kill. These scheduled removals isolate outcome evaluation and ownership cleanup; they do not establish weapon-driven transport or cargo damage.

`carrier_removal` removes the carrier at the same two times. Before delivery, production `ReleaseMe` detaches the robot into its falling state and marks it for death. Its next logic tick enters the dying state, which no longer contributes to survival; elimination occurs at 2,020 ms and defeat opens at 4,030 ms. Removing an empty carrier after landing leaves the robot alive and its side active through 10,000 ms. No kill credit is awarded. Synthetic debris and crater definitions let the normal dependent robot death execute; the test does not replace it with a direct cargo deletion.

`carrier_damage` repeats the carrier-loss schedule through production laser damage: a one-point nonlethal hit leaves the side active, then the remaining 999 points destroy the carrier. Attached cargo dies without a robot-kill credit, with elimination at 2,020 ms and defeat at 4,030 ms; already delivered cargo survives through 10,000 ms. These outcome assertions are shared with the scheduled-removal case so the two entry paths retain identical survival expectations.

`transported_robot_damage` instead applies lethal laser damage directly to the last robot at 1,000 or 7,000 ms. With the enemy damage multiplier explicitly set to 1, the robot enters its dying state and the attacking side receives exactly one robot kill. The 1,000 ms case first verifies that the robot is carried, then checks its detachment from the live carrier; at 7,000 ms it has already landed. The next status scan eliminates the player at 2,020 or 8,050 ms; the defeat dialog opens exactly 2,010 ms later and pauses the simulation. Boundary assertions reject an early result, and kill credit remains one after the delay. Both damage contracts call receivers directly: they establish damage, dependent lifetime and outcome behavior, not weapon aiming or projectile collision.

The NAV-03 `game.navigation.delivery_carrier_damage` contract covers carrier/cargo lifetime during delivery. These outcome contracts add the nonlethal-hit boundary, side-status transitions, result timing and kill attribution; they do not replace that navigation evidence.

Non-player carrier requests are reachable through the Debug F command on a traced enemy building; normal reinforcement calls use player buildings. Their player-owned cargo is recorded as a legacy quirk (Q), not as intended ordinary-play ownership.

Transport tests use body-only carriers; they do not cover weapon-attached delivery models, projectile targeting/collision with carriers, native robot portraits, restarting a loaded map or menu actions while a result is pending. O3 selects the reachable weapon-attached carrier variant; unused combat-flyer construction/firing paths are not an additional gameplay requirement. They close the explicit transport-only outcome gap without establishing the complete OUT-02 or OUT-03 catalog entries.

## Result and menu callbacks through the form

The callback fixture creates opaque 2x2, 3x3 and 4x4 bitmaps, registers them through `CMatrixHint::SetRuntimeBitmap`, and supplies font-free templates with the required copy anchors. `CMatrixHint::Build` parses them and uploads the resulting managed texture using the existing synthetic device. Real interface elements receive production `CreateHintButton` bindings; `CFormMatrixGame::Keyboard` dispatches Enter and Escape. No game package, window, font substitution or production seam is needed. Exit, Restart and Surrender use distinct widths, asserted immediately after E/R/S, so routing R to Exit cannot pass. Fixture teardown leaves dialog mode and unregisters all bitmaps before releasing their storage.

The fixture explicitly requires native display to be disabled, so post-battle statistics takes the exit fallback rather than the standalone next-map selector. It validates callback ownership and state transitions, not fonts, rendered appearance, mouse hit testing, restarting a loaded map or the original host's outer loop. These additions extend OUT-02/OUT-03 and MODE-01; the remaining coverage map still applies outside the named callback paths.

These callback tests stop when production requests `GFLAG_EXITLOOP`. No further map tick is submitted after that request. They establish the state at the exit boundary, not that `L3GRun` stops dispatching ticks or that the outer loop cleans up the game. Loop termination while orders are active remains O5/O8 work.
