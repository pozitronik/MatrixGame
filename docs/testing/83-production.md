# Construction and production contracts

The `game.production.*` contracts characterize production functions from reference source `a64e9db4595bf06cc456772cb02c70f6a34b6804`. They contribute to ECO-01, ECO-02 and ECO-03 in the [behavior catalog](../research/75-behavior-baseline/README.md); they do not complete those families or the whole-game baseline. No production implementation is replaced or changed.

## Run

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.production\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.production\.'
```

The tests link `MatrixGameInternal`. The queue executable uses the `CommandWorld` allocation/map fixture; the scenario executable uses the shared battle `Session`. Buildings, queued robots, cannons, constructor definitions and interface objects are production objects. Map allocation uses the engine allocator, matching startup: nested legacy objects rely on its zeroed storage before their constructors run. Configuration, prices, timings and module definitions are synthetic; no external packages, graphics device or audio backend are needed. Checks remain active in Release and the executable checks for tracked allocation leaks where instrumentation is enabled. Each CTest case starts a fresh process.

The queue executable contains focused subsystem contracts, not complete map-tick traces. The additional production scenario executable uses the existing battle session and non-rendering device; its scope is documented in [Synthetic building fixtures](building-fixtures.md). In particular, the income tests call production `CMatrixBuilding::LogicTakt` with explicit elapsed intervals while map time stays at zero, avoiding unrelated capture scans. They establish payout arithmetic and boundary behavior, not capture timing or whole-battle scheduling.

The queue reinforcement gate, disabled and scaling cases run Park-Miller and LegacyCRT with seed 83 and assert zero raw draws. Both modes also run the scenario cases for AI/player purchase, constructor assembly/capacity/deployment, queue deployment, base exit, maintenance clock, scheduled income, paused production, cancellation during spawn and landing rejection. Exact draw assertions cover different boundaries: AI purchase consumes one proposal-selection draw, while shortages and a second purchase blocked by a nonempty queue consume none; player purchase and computer constructor assembly/deployment consume none; player queue deployment consumes one build-sound choice; pausing consumes none. Occupied and incompatible reinforcement requests consume one approach-angle draw; the over-budget request consumes eleven draws, including ten rejected proposal choices. Other assertions establish accounting, timing or ownership without claiming an exact draw schedule for the whole scenario. The focused queue, price and income component cases do not claim RNG-sensitive coverage.

Native rendering and audible output do not participate. Constructor and purchase scenarios use synthetic material geometry and CPU texture storage; other deployment scenarios use the original surface-free CPU geometry.

The queue fixture deliberately does not pretend that `AddItem` debits a price: production callers own debiting. Tests start from declared balances and check the refund operation itself. Similarly, the AI/constructor comparison constructs matching module definitions through public production APIs; it does not execute a rendered construction panel or `BuildRobot` strategy.

## Remaining baseline work

ECO-01 still needs configured capacity/attachment rules across all component families, rendered constructor interaction, reservation and delayed strategic proposals, multiple requested units versus queue capacity, broader assembled-robot base-exit variants, and damage-driven base destruction during production. Synthetic material surfaces now permit real non-player constructor assembly, including the repair-equipped AI purchase below. The player purchase callback now uses the reviewed unavailable-icon profile, exercising the production icon-allocation failure path. Successful native icon rendering and rendered constructor interaction remain outside this evidence. The bounded strategic profile does not establish multi-base choice, weighted competing armed proposals, repair/bomb alternation or enemy-strength response.

ECO-02 still needs real click-time turret placement and rejection, ownership/destruction during active construction through the game routes, and income alongside actual ownership capture rather than explicit neutralization. The turret queue test starts with already-created production cannons and does not assert placement eligibility, autonomous turret combat or native progress-bar rendering.

ECO-03 now has real keyboard/help-callback requests, mixed occupied/free reservations, bounded proposal selection and seed/mode negative controls, difficulty scaling, carrier caps and completed delivery through the shared [reinforcement fixtures](reinforcement-fixtures.md). Rendered button picking, broader armed/headed proposal mixtures, cheat input timing variants and remaining delivery coordination with NAV-03 still need evidence. All these gaps remain baseline blockers; this suite does not justify closing the construction leaf or starting structural refactoring.

## Observed behavior and legacy quirks

Three details deserve explicit expectations: queue insertion itself does not charge resources; a refund follows the queued unit's owner rather than the base's current owner; and a factory crossing several income periods in one call grants one payout and resets its period. These observations are source-backed and asserted here. They are not proposals to change gameplay, and no crash, corruption or undefined behavior is accepted as a golden result.

## Reinforcement gate fixture

The disabled-map test supplies the same maintenance percentage field that map loading populates. A test-only derived declaration forms a protected member pointer and applies it to the actual `CMatrixMapLogic` object; it neither downcasts that object nor replaces a production function. Zero percentage rejects requests even when the cooldown is already zero or negative. A queued robot is retained unchanged throughout the rejected requests.

The scaling examples use exact integer float32 products: configured delay 1000 with map percentage/difficulty pairs 25/0.5, 50/1, 100/1.5 and 175/2 produces 125, 500, 1500 and 3500 ms. Zero difficulty or zero configured delay produces zero cooldown while leaving reinforcement enabled. Positive cooldowns, including one remaining millisecond, reject a request; resetting or reinitializing the timer consumes no RNG and changes no resources or queue ownership. These cases do not call a successful zero-cooldown request and do not establish landing, carrier creation, resource-backed robot assembly or delivery.

Timer clearing exercises `ResetMaintenanceTime` only where `_DEBUG` or `_TRACE` exposes that helper. Release uses the ordinary `SetMaintenanceTime(0)` setter. This does not establish that a reset shortcut is available in a Release game or validate its keyboard dispatch.

The landing-rejection cases use the four-place navigation fixture and call the production request method after its cooldown gate opens. Occupancy is expressed through each live robot's reserved place, which is the input `Maintenance` reads. Incompatible places carry all five chassis exclusion bits. The over-budget table contains only the rejected score 131 and no assembly data, so an unexpected attempt to create a carrier cannot silently pass. These profiles use both RNG modes with seed 83 and unavailable audio; they do not establish audible acknowledgements or delivery. Occupied, incompatible and over-budget requests share the [carrier-cap legacy quirk](reinforcement-fixtures.md): `InitMaintenanceTime()` and `S_MAINTENANCE` execute before the occupancy, compatibility, budget and cap filters. The player can therefore receive an acknowledgement and lose the cooldown without a delivery. These tests record that quirk for compatibility; they do not endorse it as intended behavior. Audible output remains outside this profile.

Queue fixture ownership transfers immediately after successful insertion, before assertions, so a failing assertion cannot leave both the queue and a local smart pointer owning the same robot.

## AI purchase and ownership loss

The purchase profile loads the synthetic definition `W,1S,R` through `SSpecialBot::LoadAIRobotType`: wheel chassis 2, Birex armour 1 and one repair weapon 10. Its real attachment record accepts that weapon at matrix 2. Module prices are respectively `(11,12,13,14)`, `(21,22,23,24)` and `(31,32,33,34)` in titanium/electronics/energy/plasma order, yielding the explicit total `(63,66,69,72)`. A second definition, `W,1S`, provides an affordable headless/unarmed alternative after the initial repair purchase, so the queue-gate check is not masked by the repair-history filter. The material cache contains all three production model/texture names. `BuildSpecialBot`, `WeaponInsert`, `RobotWeaponInit`, `RNeed` and `LoadObject` execute without replacements. These checks cover assembly and accounting, not repair targeting or rendered icons.

Before purchase, the four default robots are removed and the side runs its real regional analysis with no base or definitions. One registered computer base is then added. The definition is repair-equipped because a side with no production history initially requests a repair robot. A zero wait multiplier disables income forecasting in this bounded scenario. Exact funds buy one robot and consume one proposal-selection RNG draw; being short by one unit of any resource produces no queue entry, history update, debit or draw. A second call with sufficient replenished funds preserves the existing queue and balances without another draw. Both RNG modes execute these contracts.

The ownership-loss cases start with the same purchase and zero remaining funds. At 99 ms of a 100 ms build, neutralization or explicit map deletion cancels the queued robot and restores the exact paid total to side 2. Repeated neutralization followed by deletion produces no additional refund, and player balances remain unchanged. This pairs an actual AI debit with queue-lifetime refunds; it does not claim the computer voluntarily cancels construction or that deletion was caused by combat. Rendered constructor interaction, affordability/capacity rejection through the UI and destruction during combat remain distinct baseline gaps. Player callback payment and queue refunds are covered below.

## Player purchase callback and deployment

`game.production.player_purchase` executes `CConstructor::RemoteBuild`, the build-button callback, for one or three unarmed wheel/Birex robots in both RNG modes. It supplies a matching constructor preset and the exact purchase funds; production assembly, icon failure fallback, quantity accounting, resource debit, saved design history and counter reset are asserted. One branch calls `CBuildStack::DeleteItem(1)` directly to cancel queued robots in order and verify each refund. This is the production component invoked by the head stack-icon handler; stack-icon picking and dispatch are outside the case. Another branch advances the full map through production, base exit and door closure, checking built statistics, live robot identity, restored manual control and unchanged post-payment balances. The source base participates in map ticks, with its income interval deliberately beyond the bounded test. The case does not claim rendered constructor activation, pointer picking, affordability rejection, queue-capacity enforcement through the UI or successful icon rendering.
