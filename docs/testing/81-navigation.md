# Navigation and local movement contracts

These tests extend the synthetic battle runner with production navigation, group movement and carrier lifetime checks. They implement part of [the navigation baseline](https://github.com/pozitronik/MatrixGame/issues/81); the remaining catalog variants below still block completion of that issue and the whole-game baseline. No production movement algorithm or gameplay rule changes.

## Running the suite

```powershell
.\tools\test.ps1 -Configuration Debug -Filter '^game\.(navigation|scenario)\.'
.\tools\test.ps1 -Configuration Release -Filter '^game\.(navigation|scenario)\.'
```

The `game.navigation.*` family has thirteen named cases. Assertions use `MG_CHECK` in both configurations. The existing `game.scenario.*` cases verify that adding map variants leaves the original runner operational. All fixtures are generated from code; no game packages, display window or native audio device are needed.

## Geometry and execution

`BattleGeometry` builds the same 64-by-64 movement grid, flat terrain groups and storage-format chassis mesh used by the original controlled scenario. Its default central obstacle is unchanged. Additional layouts provide open ground, a vertical wall with a four-cell gap, a U-shaped dead end, and a closed barrier. The closed barrier has two disconnected zones and regions, with places linked only within their own side. The corridor's place links pass through its gap. These are navigation fixtures, not substitutes for loading a production map package.

Local search contracts call `FindLocalPath`, `CanMoveFromTo`, `OptimizeMovePath` and `PlaceFindNear` directly on the production map. The region case constructs a separate five-region production `CMatrixRoadNetwork`: two equal alternatives connect regions 0 and 3, and region 4 is disconnected. This component case does not claim to exercise the complete zone/road/crotch route-selection hierarchy.

Movement cases dispatch production context or group commands, then advance `CMatrixMapLogic::Takt` through the shared `Session`. Open-ground formation runs use both RNG modes and both 10 and 16 ms schedules; corridor, disconnected-region, opposing-flow, mixed-chassis and removed-blocker runs use both RNG modes at 10 ms. The seed is 79. The original runner's camera, fake audio completion policy and floating-point profile apply. No rendering occurs. Profiles are printed with revision, compiler, build options and `navigation_layout`; traces from different layouts must not be compared as the same scenario.

For opposing flow, setup adds two friendly wheel robots at (500, 200) and (540, 260), outside the original selection. The selected pair receives a context command to (500, 230); the additional robots receive separate `PGOrderMoveTo` commands to movement cells (8, 18) and (8, 24). Existing enemy robots remain present and their production AI continues to tick. The test checks that the opposing groups pass each other and finish on the intended sides, with finite coordinates and a nonzero minimum separation. It observes motion frames, not internal CPU work.

The mixed-chassis fixture adds one tracked robot at (100, 320) to the selected wheel group. Its configured speed is 0.3 world units per logic step, compared with 0.6 for wheels; rotation, structure and terrain coefficients are specified in the test. It uses the genuine track movement path and landscape-spot creation with the wheel fixture's synthetic spot resource. The test checks distinct maximum speeds, common logic-group membership, completion for all three robots and an empty tracked-robot order queue. This does not cover pneumatic foot attachment animation, antigravity flight, hover/water restrictions or slope traversal.

The blocker case adds an unselected, unordered friendly wheel robot at (300, 220), then removes it through `StaticDelete` before frame 300 advances. Both selected robots must finish at their allocated positions. This exercises removal during navigation; it is not a combat death or wreck collision scenario.

## Evidence and measurement

Open-ground, corridor and disconnected movement cases write JSONL files under the selected build's `tests/navigation-traces` directory. Each file contains the build/profile header, frame-zero context command, every completed frame snapshot and a completion footer. Each boundary is flushed, so a failed run retains its last completed observation. Filenames encode layout, RNG mode, timestep and repetition. Open-ground cases run twice in the same process and compare every snapshot exactly; this detects leaked session state. Use `tools/compare-battle-traces.py` for comparisons between separately captured files, applying the comparison rules from [the time/RNG investigation](../research/76-battle-determinism/README.md). Do not treat same-build repetition as a historical golden trajectory or a native-render equivalence check.

The local route helper prints `route_points` and `reached_cells`. The latter counts initialized movement-grid cells whose production search label `m_Find` is nonnegative after the call. It is a read-only search-footprint measurement; it is not the number of queue expansions or elapsed CPU time. The obstacle case freezes 2,951 reached cells and the crowded-destination case freezes 2,693. It is suitable as a deterministic observable beside a benchmark, but internal per-frame replanning/avoidance work counters remain absent. Adding a production counter would require a separately reviewed minimal observation seam.

The public scenario's seed, headless policy and generated fixtures differ from a native battle. Historical traces, three fresh-process runs, cross-compiler comparisons, complete DLL validation and performance acceptance belong to the integrated baseline evidence. Passing this suite alone does not establish those results.

## Delivery fixture still needed

The carrier's normal `ApplyOrder(FO_GIVE_BOT)` route constructs an `SSpecialBot`, generates textures, loads chassis/armor attachment geometry, calculates bounds and loads a flyer model before it can advance its trajectory. The current chassis fixture deliberately supplies neither the assembled robot catalog nor the flyer model/texture configuration. A faithful next extension must provide those synthetic resources and exercise the original creation route, coordinated with construction and combat fixtures. Calling `Carry(nullptr)` directly establishes payload state transitions; it cannot prove that a flying carrier reaches its release point. Bypassing the model load or setting the private trajectory position would not provide the missing baseline evidence.
