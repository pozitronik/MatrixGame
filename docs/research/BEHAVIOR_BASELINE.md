# Whole-game behavior baseline: proposed acceptance contract

This is a research proposal for [the behavior-catalog investigation](https://github.com/pozitronik/MatrixGame/issues/75), not a declaration that the baseline exists or that structural refactoring may begin. The catalog describes evidence to collect before that decision. The maintainer must accept its scope and reference-selection procedure before dependent implementation is claimed.

## Reference and evidence

The source inspected for this proposal is integration revision `540251d4662c590bad4684df01e0c521e6c4aee7`. It is the initial reference candidate, not an approved permanent oracle. No unmerged feature is part of this candidate. Source links below identify files and symbols; evaluate their implementation at that revision when reproducing the investigation.

The [existing testing guide](../TESTING.md), [test registrations](../../tests/CMakeLists.txt) and production implementations establish several useful local contracts. They do not establish a complete battle replay. For example, [bomb tests](../../tests/bomb_order_tests.cpp) seed a low-level movement order and group state before calling `TaktPL`; [selection tests](../../tests/selection_tests.cpp) substitute rectangle hit results. Both protect real behavior within their boundaries, but neither proves that a complete player command reaches a moving, fighting robot on a loaded map.

The following distinctions apply throughout the catalog:

- **Characterized** means an executable test already checks a stated local contract. It does not mean the whole row is covered.
- **Source-derived** means an implementation path has been identified; its observable result still needs measurement on the reference.
- **Unknown** means a required scenario or comparison rule has not been established. Unknowns block acceptance; they are not permission to invent an expected result.
- **Defect** requires a reproduction and a separate disposition. A crash, memory corruption or undefined behavior is not a golden expectation to preserve. If correcting it demonstrably changes gameplay, obtain a maintainer decision about that change.

## Choosing and updating the reference

1. Accept a finite version of this catalog, including the scenario variants below, and select a reviewed `dev` revision. Record its full commit, compiler and dependency versions, build flags, EXE/DLL role, Debug/Release configuration and executable hash. Record cheats, game configuration and both supported RNG modes. Freeze the exact command sequence and frame/logic-step schedule for each scenario; the reproducibility investigation determines what can be controlled without changing behavior.
2. Give each fixture and expected-result set a version. Public fixtures must be synthetic. For optional original-resource runs, keep packages local and record resource identities without uploading their contents. Distinguish packed and text startup and effective overrides: the same loose configuration beside a packed file does not necessarily take effect.
3. Establish expected observations from the reference with a human-readable explanation of the rule and a source trace. Run each core scenario at least three times in a fresh process and a repeated-session case in one process. Use exact equality only where these runs justify it. Publish first-divergence evidence when they disagree; do not approve a noisy golden file.
4. Compare a candidate against that reference using the same fixture, command order, RNG mode, build variant and supported schedule. Keep each mode's expectations separate. A change to compiler, rendering/effect execution or timing requires its own comparison; cross-compiler whole-battle bit equality is not assumed.
5. When independently developed features enter `dev`, add or amend affected catalog rows and test those features before refreshing the baseline. Record the old/new revision, intended differences, unaffected comparisons and maintainer acceptance. A reference change must never silently bless an unexplained regression.

Three runs are a minimum check for obvious instability, not a statistical proof. Seed sets, schedule variants, tolerances and stronger repetition requirements must follow [time/RNG research](https://github.com/pozitronik/MatrixGame/issues/76). Until that research is reconciled, replay and timing assertions remain provisional.

## Observation and assertion rules

Use semantic observations: selected entity identities, accepted command intent, group membership, movement cells and world positions, current order phase, target identity, health, resource balances, queue contents, capture progress, side status and exit result. Keep pointer addresses, padding, cache pointers and allocation order out of goldens. Preserve list order when the engine uses it to choose a target or place; sorting that order away could hide a gameplay change.

Integer balances, identities, membership and discrete transitions should normally compare exactly. Floating trajectories need a measured, per-field tolerance and explicit units; a broad global epsilon is not acceptable. Time-sensitive transitions should be compared at agreed simulation boundaries, including one boundary on either side. Native presentation checks compare visible/audible behavior separately from simulation outcomes.

Every scenario must assert both the intended effect and relevant forbidden effects: an invalid command must not spend resources, move an unrelated unit or retain a dead target. A successful command submission is distinct from eventual completion. Autonomous retargeting, formation placement and interruption belong in the trace even when they look inconvenient to a player. A timeout is a failure with the last observations, not a successful run with fewer assertions.

Use a narrow deliberate perturbation during test development to demonstrate that the important assertion detects the wrong behavior, then remove that perturbation. This is especially valuable for golden traces and tests that only verify invariants. Do not claim mutation testing of the existing suite from this proposal.

## Execution layers and ownership

The fixture work in [the controlled-scenarios leaf](https://github.com/pozitronik/MatrixGame/issues/79) supplies the common runner; it does not own every behavior assertion. The command, navigation, combat, economy, AI, outcome, format/host and presentation leaves own the catalog rows above. Their PRs must identify scenario IDs, normal/boundary/failure variants, exact assertions and remaining gaps. A shared fixture may serve several leaves without duplicating its ownership.

| Layer | What it must establish | Limit |
| --- | --- | --- |
| Public synthetic CI | Production command/rule/navigation paths, deterministic local contracts, bounded scenarios, invalid commands, lifetime and format checks in Debug and Release | No private assets or interactive desktop requirement; service substitutions must be declared |
| Resource-backed automation | Full preparation, real collision/mesh/resource integration and scripted scenarios with recorded resources, configuration and binaries | Optional resources cannot be redistributed; lack of a CI asset license does not excuse missing synthetic core coverage |
| Native/manual evidence | Actual window/focus/display, audible output, visual results and original-host integration that the runner cannot yet reproduce | Procedures and expected outcomes must be precise; manual-only core gameplay rows do not satisfy the gate |

The first runner scenario should issue a player move around an obstacle, replace the order while moving, then remove a targeted object before the next evaluation. It must assert transitions and bounded continuation, not merely process survival. The [fixture investigation](https://github.com/pozitronik/MatrixGame/issues/77) determines the minimum seams and feasible geometry. Resource-backed comparison should repeat the same intent using native input as an integration cross-check.

## Whole-game acceptance gate

The behavior work package can be accepted only when all of the following are reviewable together:

1. A maintainer-approved catalog and reference manifest, with every required variant mapped to an executable scenario or explicitly native presentation/host procedure. No core gameplay row may be deferred as manual-only.
2. Debug and Release results for the supported x86 standalone configurations and x86 DLL contracts, with the existing MinGW/MSVC CI matrix preserved. Both RNG modes, packed/text startup and relevant compile-time variants are represented; use targeted additional combinations where their behavior differs rather than claiming an unrun full Cartesian matrix.
3. Reference/candidate traces and assertion rationale, repeated-run evidence, known comparison limits and dispositions for every unexplained difference. A crash or corruption requires a separately reviewed fix, not an updated golden file.
4. Coverage and representative performance evidence from [the measurement work](https://github.com/pozitronik/MatrixGame/issues/78), mapped to this catalog. A high line percentage cannot compensate for an untested command, state transition or ownership contract.
5. Repeated-session cleanup checks, real-resource/native evidence, independent review and an explicit recorded maintainer acceptance of the complete baseline. Merging one test leaf does not open a local refactoring exception.

The gate is global. Small, separately reviewed test seams are allowed before it only when they preserve behavior and are necessary to observe or exercise existing paths. Structural ownership changes, RNG-stream separation, a new simulation scheduler and broad extraction of gameplay services remain gated.

## Remaining decisions and bounded follow-up

Accept or amend this catalog and the reference candidate first. Reconcile exact clock/RNG control and comparison limits with the time/RNG investigation; then finalize scenario manifests and approve the production fixture design. The current proposal introduces no additional remote issues: the planned leaves cover the identified families. If a row proves too large, propose a bounded sibling with retained coverage ownership rather than silently dropping variants.

Future settings, map-selection, music and save/load features must enter the catalog when their reviewed implementations become part of the selected reference. This proposal does not claim their unmerged behavior or freeze plans as current gameplay.

Validation of this investigation consists of tracing the cited production entry points and inspecting existing test registrations/fixtures. No full battle, reproducibility experiment, original-host run or baseline acceptance has been performed by writing this document.
