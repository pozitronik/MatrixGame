# AI players and assistants through structured game control

This report answers [the AI gameplay investigation](https://github.com/pozitronik/MatrixGame/issues/101) against source revision `a64e9db4595bf06cc456772cb02c70f6a34b6804` and the reviewed [automation protocol proposal](../99-automation-api/README.md). The protocol is a design; there is no delivered external control endpoint or playable external AI at this revision. The findings below establish source constraints and propose experiments. They do not demonstrate better play, lower workload or fair competition.

The useful first experiment is an optional adviser that observes the ordinary player view and recommends one bounded objective. A later, explicitly accepted handoff can let it execute ordinary commands until the player intervenes. An opposing controller and simultaneous delegation of several groups require additional authority and observation contracts; neither follows automatically from adding the proposed API.

## What the existing robots already do

The game's AI has several levels. [`CMatrixSideUnit::LogicTakt`](../../../MatrixGame/src/MatrixSide.cpp) calls `TaktHL` and `TaktTL` for non-player sides and for the player side in automatic mode. These functions manage strategic/team decisions, including regional actions and production. Normal player-side execution instead maintains selection/groups and calls `TaktPL`. An external player controller would supply intentions to that latter route; it would not replace all robot reasoning.

Player orders in `PGOrder*` become group intent, destination and optional target. `TaktPL` evaluates that intent, assigns places and invokes tactical combat/repair routines. Its ordinary evaluation is throttled by a 100 ms game-time check, and command handlers can call it synchronously. `WarPL` considers the commanded attack target together with the robot's environment; capture combat also considers cannons attached to the target building. `PGFindCaptureFactory`, `PGFindAttackTarget` and `PGFindDefenceTarget` already provide autonomous group objectives. Below them, [`CMatrixRobotAI::LogicTakt`, `LowLevelMove` and `WallAvoid`](../../../MatrixGame/src/MatrixRobot.cpp) execute orders and movement with local collision/avoidance behavior.

Consequently, a dispatched attack is neither a guaranteed immediate shot nor a promise to remain at the selected point. Local movement and targeting decisions continue between external decisions. An adviser can explain the difference between the requested objective and observed progress, or suggest a different objective. It cannot claim to cure navigation or tactical behavior merely by issuing the same order more often. Repeated selection and orders can also change group state, acknowledgement sounds and the shared RNG stream; the [protocol's command-equivalence analysis](../99-automation-api/README.md#rng-and-execution-inputs-for-equivalence) is part of the experiment contract.

The existing auto-attack, auto-capture and auto-defence commands are important comparison policies. A new controller should first demonstrate a benefit over those capabilities, rather than receive credit for behavior the engine already supplies. Automatic player-side mode is a separate whole-side mode: the proposed API denies control in that mode, so enabling it is not a way to combine two independent commanders.

## Candidate modes and their authority

| Mode | Useful outcome to investigate | Information and commands | Conflict policy and delivery boundary |
| --- | --- | --- | --- |
| Observe-only cooperative adviser | Help a player notice idle forces, changing contacts or an unfinished objective, with fewer distracting checks | Player-profile observations only; no selection, camera or game mutation. Advice records its observation boundary and uncertainty | Player remains sole commander. Present recommendations in a separate client initially; an in-game overlay is separate UI work. Feasible once observation is implemented, but unmeasured |
| Cooperative handoff | Carry out one accepted objective while the player watches, reducing repeated orders | One normal player lease; only advertised commands, current selection and eligible targets | Human input revokes the lease. Already dispatched game orders continue. Return control explicitly when the objective ends, expires or needs a decision. Fits the proposed exclusive lease, without simultaneous human command entry |
| Delegated group controller | Let the player command one force while a helper handles another | Ultimately needs an explicit owned-entity set, side-limited observations and a definition of permitted objectives | Concurrent delegation does not fit the current single lease and shared selection. Start only with the handoff experiment restricted by client policy; server-enforced group authority and independent selection need a separately reviewed protocol extension |
| Opposing AI player | Provide a different strategic opponent or an adjustable challenge | A future side-scoped command/observation capability, with a reviewed information policy and resource/production rules | Current commands target `PLAYER_SIDE` only. Replacing another side's `TaktHL`/`TaktTL` decisions needs an explicit engine boundary while retaining robot execution. This is future implementation, not an available use of the player MVP |

A group-limited client under a whole-player lease is an experimental convention, not an enforcement boundary. It still shares the player's selection and can affect group formation, camera and acknowledgement state. Do not advertise it as safe concurrent delegation. A later group lease must define membership changes, splitting/merging groups, destroyed units, control-group recall, production/deployment into a group, direct-control takeover and whether camera/selection actions are globally exclusive. The current protocol deliberately requires a separately acknowledged selection revision instead of arbitrary actor lists attached to each order.

For an opponent prototype, an external controller may command the ordinary player side against existing computer sides in a diagnostic evaluation. That measures its ability to play from that seat. It does not deliver a new opponent against a human, prove symmetry between starting positions, or justify granting access to another side's internal state. Adding side-specific control by changing `PLAYER_SIDE` or enabling automatic mode would bypass the reviewed command contract.

## Observation and fairness

Use the protocol's player profile for every player-facing trial. [`CMinimap::Draw`](../../../MatrixGame/src/MatrixMinimap.cpp) iterates global contacts without a per-side knowledge filter, so imposing a new fog-of-war rule would change the game. Conversely, a visible minimap icon does not expose exact health, intended target, path, production queue or unquantized world position. Its type/liveness rules also differ for flyers. The [field provenance table](../99-automation-api/README.md#information-available-to-clients) must remain authoritative: enable a field only after matching the native display/picking surface, with its observation source and precision. Scene targeting still requires the applicable scene eligibility; a minimap contact alone does not authorize an object-targeted attack.

Diagnostic access can expose exact state and internal intent for evaluation. Keep that recorder outside the controller's input path. Store separate controller-visible observations and privileged evaluation records so an audit can establish what informed each decision. Any omniscient comparison is explicitly a privileged upper-bound experiment, not evidence of player-information parity. Do not silently feed diagnostic target positions into a supposedly fair controller when a player field is unavailable.

Information parity is only one part of fairness. A program can attend to every allowed contact, remember indefinitely and submit commands much faster than a human. Log reaction delay, decision rate, command rate and observation frequency; evaluate explicit limits rather than claiming that using the same commands makes an opponent equally capable. For cooperative assistance, the relevant product question may instead be whether the player understands and welcomes that advantage. Neither question is settled by this research.

## A bounded decision cycle

The client should operate on objectives such as moving a selected group to an agreed point. It consumes a completed observation, chooses from advertised operations, obtains authority if appropriate, selects through the supported route and dispatches an order with the current selection revision. It then awaits progress or an invalidating event. `received` only means queue admission; `command_result: dispatched` means the native command route ran. Arrival, capture and survival must be evaluated later from permitted observations. Define the completion predicate, time limit and reasons to ask the player before starting the objective.

Keep model or planner computation outside the engine process. A deterministic rule-based client is a useful first comparator and transport exerciser; a learned planner or language-model client may use the same protocol later. No vendor, network service, framework or model format is required by this proposal. A planner produces constrained proposed actions, and a client-side validator checks capabilities, authority and freshness before submission; the engine remains the final authority. Natural-language text must never become arbitrary engine commands or memory edits.

Observation age must be checked again after a long computation. For a proposed attack, re-observe target eligibility, selection and session before dispatch; reject or recompute a stale decision rather than replaying it. Use hysteresis or an objective-level cooldown to avoid changing destination on every observation, but treat those as controller policy under test. Do not impose an unmeasured cooldown on the original game. Avoid per-frame replanning until measurements show a useful need.

### Latency and interruption

The protocol proposes at most ten periodic snapshots per second and bounded command queues as initial limits. These are not measured capacity or latency promises. `TaktPL`'s 100 ms check does not establish a universal 100 ms AI reaction interval: synchronous command effects, other update paths, rendering and loop scheduling all contribute. Measure observation age at decision start, planner wall time, admission-to-dispatch time, dispatch-to-observed progress and game frame-time overhead separately. Report median and tail distributions, timeouts and rejected requests; a fast IPC exchange is not evidence of a fast tactical response.

Run strategic decisions asynchronously while the game continues normally. Test injected decision delays of 100 ms, 500 ms and 2000 ms as experimental conditions, not acceptable-performance promises. Use one recorded schedule per deterministic diagnostic comparison, and separately evaluate realtime foreground play. A slow decision should expire harmlessly; it must not freeze the engine or silently pause the battle. Paused/inactive observations include their actual game time, so the client must not interpret repeated wall-clock polls as battle progress.

Native focus loss revokes the proposed control lease, and the ordinary inactive-window policy stops simulation unless existing keep-alive behavior applies. A background client can operate while the game stays foreground. Switching to an adviser window may suspend the battle; a seamless interactive adviser UI therefore needs a separate design and native validation. Connecting a controller must not silently enable keep-alive, speed controls or diagnostic advancement.

| Event | Proposed client response, following the protocol |
| --- | --- |
| Human selection, command, camera action, active drag, relevant shortcut or focus loss | Honor lease revocation immediately; abandon pending plans and do not automatically reacquire. Let native input proceed |
| Target/selection/session changed | Re-observe; discard the invalid plan. Do not manufacture a replacement target from hidden state |
| Planner timeout or unavailable external service | Emit no new mutation; explain that assistance stopped. Ordinary dispatched orders remain active |
| Disconnect or lost command result | Reconnect and reconcile state/status. Never blindly replay an uncertain mutation under a new ID |
| Queue saturation or output overflow | Follow bounded retry/disconnect rules; avoid unbounded plan accumulation and discard obsolete plans |
| Battle end, restart, dialog or automatic mode | Stop strategic dispatch; retire old IDs and authority as required. Never dismiss dialogs or restart without an advertised, authorized operation |

Releasing the lease does not stop the robots. This distinction must be visible to the player: assistance has stopped issuing instructions, while the last accepted move or attack continues. An explicit stop is a separate ordinary command requiring current authority. Direct-control held keys, bomb orders, spending resources and autonomous surrender are excluded from the first handoff trial; their consequences and ownership need their own acceptance criteria.

## Evaluation before claims of improvement

The test infrastructure can establish command semantics and provide repeatable scenarios. It cannot establish whether an assistant is pleasant to use. Separate three forms of evidence: protocol/authority correctness; controlled gameplay comparisons; and player trials measuring usefulness and unwanted intervention. The [current battle scenarios](../../../tests/battle_scenario_tests.cpp) cover synthetic movement, replacement, target removal, repeatability and observation effects. They do not implement an AI endpoint, prove full battle coverage or validate the candidate modes in this report.

For each comparison, record code/controller versions, map or synthetic fixture identity, initial forces/resources, effective settings/difficulty, seed and RNG mode, time schedule, compiler/build/options, floating-point profile, audio/effect policy and the exact controller-visible observations and commands. Use both supported RNG modes and several predeclared seeds/scenarios. Compare identical initial conditions and execution profiles, but do not require two different policies to consume equal RNG draws: legitimate differences in commands change the execution. Keep draw counts and command traces as explanatory evidence, not grounds to reseed or suppress sound/effects.

| Scenario | Comparators and measured outcome | What it can establish |
| --- | --- | --- |
| Move a group through an obstacle to a fixed destination | One ordinary move, a documented scripted policy and proposed controller; arrival/progress bounds, losses, command count, reversals and completion time | Whether additional planning helps that situation; distinguishes command churn from progress |
| Capture or defend an objective under a changing threat | Existing auto-capture/auto-defence where applicable, ordinary manual/scripted orders and controller; ownership duration, casualties, time and objective abandonment | Whether choosing objectives adds value over the built-in tactics; requires the corresponding command capability |
| Target dies or a route becomes blocked after a decision | Same observation/latency conditions; stale-command rejection, recovery time, unintended target changes and human interventions | Robustness to old information, without privileged replacement targets |
| Human interrupts a handoff | Selection, camera, command, focus and display actions during computation and queued dispatch; mutations after revocation, preserved human input and continuing prior orders | Authority correctness. Any unauthorized mutation is a failure, regardless of win rate |
| Opponent-seat battle experiment | Existing automatic-side behavior and explicit simple scripted policies, with information differences disclosed; outcomes, duration, resource use and bounded command rates | A preliminary ability comparison from that seat, not proof of balanced human opposition |
| Cooperative player trial | Same scenario family with assistance off, advice only and accepted handoff; task success, active command count, rejected suggestions, takeovers and player-rated clarity/control | Whether reduced workload compensates for interruptions. Counterbalance trial order to reduce learning effects |

Choose primary metrics and stopping conditions before running a trial; do not select only scenarios won by the new controller. Report failures and sample sizes, and retain per-scenario results rather than only an overall win rate. If a human comparison is too small to support a general conclusion, report observations as a pilot. Hard gates include no out-of-profile fields, no unauthorized post-takeover commands, no stale-session mutations and no material frame-time regression under the agreed performance budget. Numeric benefit and performance thresholds require measurements and maintainer agreement; none are invented here.

A high win rate can come from extra information, command throughput or a favorable map. A lower command count can hide a player repeatedly correcting a confusing objective. Review traces and player feedback alongside aggregate metrics. The controller should state the objective, the observation on which it acted and why it stopped; it should not claim access to an engine decision reason that the player profile does not expose.

## Bounded follow-up proposals

These are proposals for maintainer consideration, not new tracker items or authorization to implement. The [API implementation leaf](https://github.com/pozitronik/MatrixGame/issues/100) already owns transport, client tooling, observations, authority and native-command equivalence after the complete behavior-baseline gate. Do not duplicate that scope. [Player-command coverage](https://github.com/pozitronik/MatrixGame/issues/80), [navigation coverage](https://github.com/pozitronik/MatrixGame/issues/81), [combat coverage](https://github.com/pozitronik/MatrixGame/issues/82), [economy coverage](https://github.com/pozitronik/MatrixGame/issues/83), [AI coverage](https://github.com/pozitronik/MatrixGame/issues/84) and [session coverage](https://github.com/pozitronik/MatrixGame/issues/85) supply preserved behavior; they are not permission to change robot obedience for an experiment.

1. **Observation-only advice pilot.** After the API's player observations are validated, implement an external deterministic adviser for one objective family and a reproducible scenario/evaluation runner. Deliver provenance-tagged advice, freshness/timeout handling and a comparison with unaided play. No engine mutation, model service or in-game UI is required. Stop if the needed player-visible fields are not available; propose those fields with native evidence rather than using diagnostics.
2. **Explicit objective handoff pilot.** After selection/move/stop/attack equivalence and takeover tests pass, add one human-approved move objective under the existing lease, with observable completion, deadline and interruption reporting. Compare with one ordinary move command before adding combat objectives. Acceptance includes disconnect and delayed-planner cases, no automatic reacquisition and no hidden resource spending. This work delivers a client policy, not concurrent group control.
3. **Delegation contract experiment.** If handoff shows useful results, design group membership/authority and shared-selection handling before production implementation. Use synthetic races for death, reassignment, group recall and human takeover. Decide whether a global human action revokes every group or only the affected assignment. The current protocol's global revocation rule remains unchanged until a new contract is reviewed.
4. **Opponent feasibility prototype.** First evaluate the external controller in the supported player seat with explicit information restrictions and latency. A separate reviewed proposal must then establish a side-specific dispatch boundary, how original strategic AI is disabled only for that side, production/resource rules and fairness criteria. Preserve robot tactics and existing difficulty configuration unless a separate gameplay decision changes them. This is larger than adding another pipe client.

The recommended order is advice, bounded handoff, then a decision between delegation and an opponent. It gives the maintainer evidence about usefulness and command stability before introducing multiple commanders. A rule-based controller is sufficient to test the interaction; a more capable planner becomes justified only by a measured limitation and a repeatable comparison.

## Decisions to settle before a playable feature

| Decision | Recommendation for the first trial | Alternative requiring explicit scope |
| --- | --- | --- |
| Product goal | Reduce repetitive supervision while preserving human control | Stronger opponent or autonomous whole-battle completion, with different success metrics |
| Information | Verified player-profile fields and precision | Omniscient or enhanced tactical information, clearly labeled as a gameplay advantage |
| Authority | Advice, then explicit exclusive handoff with human-priority revocation | Simultaneous group/side leases and a new arbitration contract |
| Intervention budget | One bounded move objective first; no spending, bomb use or held direct control | Autonomous combat/production with separate action limits and confirmation policy |
| Failure behavior | No new commands; existing orders continue; explicit reacquisition | Automatic fallback orders, which can change player intent and require a separate contract |
| Controller choice | Local deterministic reference policy; replaceable planner interface | Optional learned/network planner after latency, availability and information-sharing choices are accepted |
| Evidence required | Authority/protocol correctness, controlled comparison and a small player pilot | Competitive balance claims, which need broader scenario/starting-position and player evaluation |

No maintainer decision is needed to accept this research as a bounded assessment. Each proposed feature still needs a scoped implementation decision, the completed behavior-baseline gate where applicable and independent review. The modernization epic can finish with the automation API and this investigation; it does not depend on delivering an AI player or assistant.

## Validation and limits

Validation for this report was source tracing of `LogicTakt`, `TaktHL`/`TaktTL`, `TaktPL`, `WarPL`, `PGOrder*`, autonomous target selection and robot movement; comparison with the approved protocol's observation, lease, timing and failure contracts; and inspection of the current production-backed scenario tests. Repository/whitespace and local Markdown-link checks cover the document itself. No controller, endpoint, benchmark or player experiment was implemented or run, so all benefit, balance and latency claims remain hypotheses with the evaluation procedures above.
