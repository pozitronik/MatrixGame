# Session lifetime

The standalone executable initializes at most one battlefield per process. The battle menu's Restart action reloads the current map's dynamic objects inside that session; it does not construct a new window or DirectX device. Choosing another map in the [map selector](MAPS.md) tears down that session and starts a new process. Repeated full initialization inside a host process is a separate contract and is not established by standalone launch tests.

## Startup and map-transition contract

Interactive standalone initialization has one staging point inside `CGame::Init`: after base services, configuration, cache, device, renderer and sound setup, but before constructing `g_MatrixMap` or the battle interface. `StartupMenu::run` owns a temporary form and its hints on that existing device. New battle opens the selector; Cancel returns to the menu without saving. Start validates and saves the map and bonus and continues the same initialization call. Exit or window close returns early with `g_MatrixMap == nullptr`. `WinMain` then skips game-form construction and the battle loop and runs the normal partial-session cleanup. The startup form detaches and releases its hints and preview before cleanup deletes their backing services.

This staging does not split initialization into reusable engine/battle services, introduce in-process battlefield replacement, or change simulation ownership. The original DLL host and ordinary command-line map argument bypass the standalone menu and bonus selection. The random seed is captured before the menu and the menu consumes no gameplay random draws. The complete behavior-baseline gate remains required for structural lifecycle refactoring. Acceptance of this bounded standalone feature does not accept the whole-game baseline or waive that gate.

The test-only `friend struct GameStartupTestAccess` grants a native test access to the existing private `CGame::ApplyVideoParams` method. It changes no layout or runtime behavior. That opt-in test draws synthetic menu buffers and fonts, invokes actual battle video setup and redraws after reset. This is a narrow test seam for the menu-to-battle transition, not a reusable initialization API. It remains unregistered because it requires a native DirectX device; asset-free CTest cases do not establish complete rendered startup.

Starting a different map saves only the map and bonus over stored preferences; temporary Alt+Enter state is not persisted. The new process uses the saved display settings. The old process completes normal session teardown, creates a readiness event and launches the same executable with `--start-selected-battle` and the private event name. Only an exact first argument matches this reserved mode. Other first arguments retain visibility-calculation semantics. A missing remembered map releases the handoff and reveals the startup menu.

The loading screen uses a separate GDI window/message thread and CRT-owned state, independent of game heaps and the DirectX device. During a relaunch the old process pumps messages while waiting for the child's readiness event or process termination. The wait is bounded to 120 seconds. Closing the loading window, pressing Escape while it has focus or choosing Hide loading screen ends that wait early. Timeout or dismissal removes the loader and lets the old process exit normally; it does not terminate the child or roll back the saved selection. The child can still finish loading and show its window. On an initial same-process load, dismissal hides the cosmetic screen while initialization continues. Loader creation failure is logged and does not abort initialization.

During the handoff the child keeps its window hidden until battlefield initialization finishes and defers exclusive fullscreen acquisition to the game form's first ticks. Its first `S_OK` battle presentation signals readiness. Occlusion, mode-change and failed presentations leave the handoff pending within the parent's deadline; a caught startup failure releases it before showing a diagnostic. A child exit also releases the parent. The loading window is not evidence of load progress, and the timeout is a presentation escape path rather than proof that a child is healthy or dead. No path initializes a second battlefield in the same process.

## Ownership

| Resource | Owner and cleanup |
| --- | --- |
| Standalone window | The 3G layer creates the window and registers its class. `L3GDeinit` destroys the owned window and unregisters its class. |
| Host window | DLL initialization borrows the host window and replaces its window procedure. `L3GDeinit` restores that procedure; ownership remains with the host. |
| DirectX interfaces | Standalone initialization owns the initial references from `Direct3DCreate9` and `CreateDevice`. `L3GDeinit` releases the device reference before the Direct3D reference and resets both global pointers. DLL initialization borrows both interfaces without taking a reference; teardown disconnects those pointers without releasing host references. Other resources can retain their own device references. |
| Game heap and configuration | `CGame::Init` creates `g_MatrixHeap` and `g_MatrixData`. `CGame::Deinit` deletes game-owned objects and configuration before deleting the heap object. `CHeap` supplies allocation helpers and Debug tracking, not an arena that frees surviving allocations when its object is deleted. Cursor-name strings use `g_CacheHeap`; `CMatrixConfig::Clear` destroys them and resets their pointer and count before cache teardown. |
| Map | `CGame::Deinit` deletes `g_MatrixMap`. Map cleanup releases objects, effects, navigation, sides, terrain, skins, sound handles, cursor resources and stored device state. Restart rebuilds dynamic content from the current map while retaining the map instance. |
| Forms | Construction registers each `CForm` in a linked list; destruction unregisters it. `FormChange` calls the previous form's `Leave`, changes the active pointer, then calls the new form's `Enter`. Detach an active form before deleting it. The base destructor is not virtual: destroy through the concrete type. |
| Texture and model cache | `CacheInit` creates `g_CacheHeap` and `g_Cache`. Normal shutdown clears game users before clearing the cache; `CacheDeinit` deletes the cache and its heap and resets their pointers. Keep this ordering because map and cursor cleanup use cached resources. |
| Text fonts | `Text::GetFont` holds a function-static collection tied to the first device supplied. Its font wrappers release their interfaces at process shutdown. The embedded font registration is also retained for the process lifetime. There is no explicit cache reset for a replacement device. |
| Timer resolution | Standalone `WinMain` records a successful `timeBeginPeriod(1)` and pairs it with `timeEndPeriod(1)` on normal completion or a caught exception. The DLL loop begins the period and normal `CGame::SafeFree` ends it. Initialization/form-construction failures call cleanup with timer release disabled because the loop has not started. |
| Cursor and keyboard | The map owns its software cursor resources. Activation can confine the system cursor to a fullscreen window; deactivation and standalone exit release confinement. Deactivation clears held keys; ending a session also clears the engine held-key table at the start of `CGame::Deinit`. Reloading a map through Restart retains input within that same session. Verify visible cursor restoration separately from object cleanup. |

## Shutdown and failure boundaries

Standalone shutdown ends any acquired timer period, detaches and destroys the game form, calls `CGame::Deinit`, clears the cache, tears down the 3G layer, deletes the cache services and ends the base services. Form detachment happens while game state is still available. Cursor confinement is released after cleanup.

Engine, standard and unknown C++ exceptions release cursor confinement, stop standalone audio and copy/log the diagnostic before running the same standalone shutdown sequence. The error dialog opens after teardown has detached the form and destroyed the game window, so its modal message loop cannot dispatch input into failed game state. Every cleanup stage is attempted even if an earlier stage throws; a cleanup exception makes the process return a failure status. `CGame::SafeFree` also tolerates a missing cache. Cleanup is not a recovery mechanism for native faults or corruption, and it does not establish reusable game state after an arbitrary partially completed allocation.

The lifecycle executable links production configuration, standalone teardown, cache, map, graphics and form implementations. Its diagnostic overlay substitute records messages and rejects rendering or device transitions. Registered cases cover repeated cursor cleanup and reload, empty configuration, form enter/leave ordering, constructor unwinding, three form lifetimes, partial startup up to an empty map, failure before cache creation, continued cleanup after C++ exceptions, owned versus borrowed reference release, and graphics configuration rejection before window creation. Partial standalone cleanup also checks gamma-state reset with no device, detecting an omitted graphics teardown stage. The fixture clears the native exception filter after each base initialization to keep crashes from opening dialogs. Debug also rejects remaining tracked heap allocations. These cases create no window or graphics device and load no game assets.

An opt-in native graphics case creates three standalone windows/devices, checks that teardown releases their initial COM references and destroys their windows, then attaches to a synthetic host window/device and checks that its procedure, window and reference counts survive teardown. It also calls teardown repeatedly. Run it on a Windows desktop with DirectX 9 after building the tests:

```powershell
.\build\mingw-debug-exe\tests\matrixgame_lifecycle_tests.exe manual.lifecycle.native_graphics
.\build\mingw-release-exe\tests\matrixgame_lifecycle_tests.exe manual.lifecycle.native_graphics
```

This case is excluded from CTest because it requires a graphics device. It loads no game resources or fonts. Successful native graphics cleanup does not establish replacement of a device with live font, map or texture resources.

Run the focused cases with `tools/test.ps1 -Configuration Debug -Filter '^game\.lifecycle\.'`, then repeat with `Release`. Follow [Standalone playtesting](PLAYTESTING.md#repeated-sessions-and-restart) for menu restart, result dialogs, process exit and cursor observations. Natural battle completion, real device recovery and arbitrary allocation failures require separate evidence.
